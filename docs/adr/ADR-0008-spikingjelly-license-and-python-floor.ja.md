# ADR-0008：SpikingJelly のライセンスは OIOSL 1.0 であり、それに伴い開発環境の Python 下限を引き上げる

[中文](ADR-0008-spikingjelly-license-and-python-floor.md) · [English](ADR-0008-spikingjelly-license-and-python-floor.en.md)

- **ステータス**：承認済み
- **日付**：2026-09-22
- **関連**：プロジェクト計画書 §1.4、§七 フェーズ 1、§八、§12.1、§12.3；[docs/references.md](../references.ja.md) の v6.3 修正待ち一覧

## Context

プロジェクト計画書 §1.4 と §八 は、本プロジェクトのフレームワーク選定として **SpikingJelly** を挙げています。§12.1 のライセンス戦略表では、ソースコードの行にこう書かれています：

> ソースコード | **Apache-2.0** | SpikingJelly との生態系互換（同一ライセンス）；特許許諾条項が産業利用者に友好的

フェーズ 1 の最初のタスクは「環境構築」、すなわち SpikingJelly を実際に導入することです。導入の前にライセンスを確認したところ、結論は上の一文と一致しませんでした。

### 事実 1：SpikingJelly は Apache-2.0 ではなく、啓智オープンソースライセンス 1.0 である

**啓智オープンソースライセンス 1.0（Open-Intelligence Open Source License、OIOSL）** です。検証可能な根拠は次のとおりです：

- リポジトリ直下に `LICENSE`（本ライセンスの中国語正文）と `LICENSES/`（翻訳と利用・配布ガイド）があります。README の License の節には "SpikingJelly is distributed under the Open-Intelligence Open Source License Version 1.0" と書かれています；
- GitHub API の `license` フィールドは `NOASSERTION` です——licensee はこれを標準ライセンスとして認識できませんでした；
- PyPI では、安定版 `0.0.0.0.14` の classifier が `License :: Other/Proprietary License`、`2.0.0rc1` の License フィールドは空です。

ライセンス正文によれば、OIOSL 1.0 の実際の条件には次が含まれます：

- ソースコード形式と実行可能コード形式の**いずれについても使用と再配布が認められます**が、ライセンス条件・ライセンス表示・免責事項を保持する必要があります；
- **商業目的での使用または再配布には、事前に AITISA**（次世代人工知能産業技術革新戦略アライアンス、aitisa.org.cn）**の公式サイトでの声明開示が必要**です。少なくとも使用者／再配布者の名称、連絡先、住所、電話、メールアドレス、使用目的を含みます；
- 特許許諾は「任意の特許声明」に置かれています：許諾者が本ソフトウェアを覆う特許を有する場合、関連特許を有さない使用者に対しては FRAND-RF／特許プールへの参加／FRAND のいずれか一つを許諾し、関連特許を有する使用者に対しては、許諾者は「権利を有するが義務を負わない」という相互原則での許諾にとどまります。

### 事実 2：本リポジトリの既存のライセンス監査はこれを黙って通してしまう

`scripts/check_licenses.py` は、ライセンス名を `FORBIDDEN_PREFIXES = ("AGPL", "GPL", "SSPL", "BUSL", "CPAL", "OSL")` と**前方一致**で比較します。`Open-Intelligence Open Source License` はこの六つの接頭辞のいずれにも一致しません。さらに SpikingJelly の wheel メタデータでは License フィールドが空であるため、`unknown` のバケツに落ちます——そして CI はこのスクリプトを `--strict` なしで呼ぶため、**unknown は表示されるだけで失敗しません**。

プロジェクト計画書 §12.3 は、ライセンス監査の役割をまさにこの種の問題を止めることだと述べています。しかしこれは止められません。

### 事実 3：SpikingJelly 2.0.0rc1 は Python >= 3.11 を要求する

`2.0.0rc1` の `requires_python` は `>=3.11` で、`torch>=2.6` に依存します。そして現代的な torch を支えるバージョン系列はこれ**だけ**です：直前の安定版 `0.0.0.0.14` は 2023-03 公開で、numpy 2 と torch 2.14 より前です。当時の root プロジェクトは `requires-python = ">=3.10"`、ローカルの Python は 3.10.11 でした。

### ついでに確認した項目

プロジェクト計画書 §八 に挙がっているもう一つの構成要素、**eprop-PyTorch は Apache-2.0** です。ライセンス自体は問題ありません。ただし最後のコミットは 2022-02-18 です。

## Decision

**1. SpikingJelly を残し、OIOSL 1.0 の条件を受け入れる。** 差し替えることは §1.4／§八 が指定する技術スタックを放棄することを意味します。また本プロジェクトにおいて SpikingJelly が担うのは二つだけです：LIF/ALIF ニューロン原始演算の提供と、代理勾配 BPTT の対照ベースラインとしての役割です。本プロジェクトは研究プロトタイプであり非商業用途であるため、商業利用の開示義務は現在の形態では発生しません。ただしこれは**下流の使用者が継承する義務**であるため、何も検出しない隅に置くのではなく、文書に書くべきものです。

**2. root プロジェクトの Python 下限を >= 3.11 に引き上げる**、SpikingJelly は `==2.0.0rc1` に固定します。

代償として、CI の pytest マトリクスは 3.10/3.11/3.12 から 3.11/3.12 に狭まります。**`biosnn-bus` 自身の `requires-python >=3.10` は変えません**——実際に numpy のみに依存し 3.10 で動きます。この対外的な宣言が root の開発環境の下限に引きずられるべきではありません。この宣言が空文にならないよう、CI の `package` job を 3.10 と 3.12 の二本に拡張します：クリーンな venv に wheel を入れ、スケルトンライブラリのテストスイートを走らせます。**変えるのは開発環境の下限であり、配布パッケージの下限ではありません。**

**3. eprop-PyTorch は読解の参考と相互検証のみに用い、依存には入れない。** ライセンスは問題ありませんが 2022 年以降更新されておらず、固定している torch API は 2.14 と合いません。e-prop は自前実装します。最も難しい箇所（ALIF の資格痕跡）では、そのソースを照合物として項目ごとに突き合わせ、**食い違う場合は Bellec et al. 2020 の原文に従います**。

**4. ライセンス監査を厳格化する：「検出できない」を「明示的に宣言しなければならない」に変える。** `scripts/check_licenses.py` に、**既知であり受け入れた**非標準ライセンスを登録する白名簿（各項目に理由と本 ADR へのリンクを付す）を追加し、新しい `--strict-unknown` を設けます：白名簿に登録されていない unknown はすべて失敗とします。CI は `--strict-unknown` に切り替え、監査前の `uv sync` に `--group research` を付けます——そうしなければ torch／SpikingJelly／gymnasium は監査の範囲に入りません。

白名簿は抜け穴であるため、各項目に理由を書かねばなりません。これは §12.5 が `EXEMPT` 表に定めたのと同じ規律です。

**5. プロジェクト計画書 §12.1 には v6.3 での修正が必要です**。「SpikingJelly との生態系互換（同一ライセンス）」を事実に即した記述に改め、OIOSL の商業利用開示義務を補う必要があります。修正が入るまで、§12.1 を引用する場面では本 ADR が優先します。

## Consequences

**利点**

- 環境構築が、検証していないライセンスの断言の上に載ることがなくなります；
- ライセンス監査が「強コピーレフトのみを止める」から「unknown は失敗、受け入れは登録必須」に変わります。OIOSL のように**コピーレフトでもなく標準的なオープンソースライセンスでもない**事例に、ようやく居場所ができます；
- スケルトンライブラリの対外的な Python サポート宣言が実質的なカバレッジを得ます（CI の 3.10 の脚が wheel を入れてテストスイートを走らせます）。root と一緒に引き上げられることはありません；
- eprop-PyTorch の位置づけが明文化され、「なぜ直接使わないのか」に答えがあります。

**代償（受け入れたもの）**

- **OIOSL の商業利用開示義務は配布に伴って伝播します。** 本リポジトリ自身の研究用途では発生しませんが、本プロジェクト（ひいては SpikingJelly 依存）を商業目的で使う者は、AITISA への開示義務を自ら負うことになります。これは ADR の中だけでなく、README の依存関係の説明に書くべきものです。
- **プレリリースへの依存。** `spikingjelly==2.0.0rc1` は厳密に固定しています。正式版になった時点で本 ADR は再評価が必要です——**とくにライセンス条項が変わっていないか**を。
- CI の pytest は 3.10 の脚を失います。3.10 でのスケルトンのテストは `package` job が担うことになり、カバレッジの方式が「ソースツリーで直接走らせる」から「wheel を入れてから走らせる」に変わります。両者は完全には等価ではありません。
- `uv.lock` が CPU と cu130 の二組の torch wheel を記録するため、ファイルは大きくなり、torch 更新時の lock の diff は明らかに騒がしくなります。

**明示的に主張しないこと**

1. **OIOSL 1.0 が「オープンソースライセンスではない」とは主張しません。** 本 ADR が記録するのは**検証可能な事実**です：Apache-2.0 ではないこと、GitHub の licensee が認識できないこと（`NOASSERTION`）、PyPI の安定版が `Other/Proprietary` と表示していること、商業利用の開示義務を伴うこと。**OSI の公式認定リスト全件は今回照合していません**（opensource.org のライセンス一覧ページはスクリプトから読めません）ので、その OSI 上の地位については断言しません。
2. **法律レビューを行ったとは主張しません。** 以上はライセンス正文の読み取りであり、法的助言ではありません。本プロジェクトの形態が変わる場合（たとえば商業スポンサーを受け入れる、ホスティングサービスを提供するなど）、再評価すべきです。
3. **自前のニューロン原始演算が等価な代替だとは主張しません。** e-prop の正しさは ALIF ダイナミクスの正確な実装に依存し、自前実装にも同じリスクがあります。SpikingJelly を残すという判断は、まさにこのリスクを持ち込まないためのものです。

- **後日の訂正（2026-09-23、外部リポジトリを実際に確認した結果）**：決定 3 のうち二文が `ChFrenkel/eprop-PyTorch` のリポジトリ事実と一致しません。リポジトリの慣例に従い本文は変えず、ここに注記します：
  1. **「2.14 では満たせない torch API に固定されている」わけではありません**——当該リポジトリには **依存マニフェストもバージョン制約もありません**（`requirements.txt` も `pyproject.toml` も CI も無し）。動かなくなった機械的な原因は `setup.py` の `dtype=np.int` 二箇所で、このエイリアスは **NumPy 1.24** で削除されました。
  2. **ALIF 資格痕跡の参照物にはなりません**——当該リポジトリは **ALIF を明示的に削除済み**です（`main.py`："Support for the ALIF neuron model has been removed."、`models.py`：`assert self.model == "LIF"`）。しかも 2022-02-18 の初回コミット一つだけで、履歴にも ALIF 版はありません。ALIF は**公式実装** [15] `IGITUGraz/eligibility_propagation`（`Figure_3_and_S7_e-prop_tutorials/tutorial_evidence_accumulation_with_alif.py` など）と Bellec et al. 2020 原文で確認してください。
  **したがって参照価値は次の範囲に狭まります**：LIF + 証拠蓄積の系列（式 (4)/(25) のハードコード実装、資格痕跡の `F.conv1d` 因果畳み込みによるベクトル化、「漏れ時定数を伸ばして秒スケールの依存を覆う」技法）。ライセンスの結論は変わりません——Apache-2.0、compliant、依存に入れても問題なし。ただし **PyPI 未公開・タグ無し**なので commit `0f32a8f2` を锚にするしかなく、実務上は読むだけの参考です。

## Alternatives

**A. LIF/ALIF ニューロン原始演算を自前実装し、SpikingJelly を一切導入しない（およそ 200–300 行）。**

却下。利点は明確です：ライセンスの絡みがゼロ、Python 下限も動かず、CI の三本の脚も保てます。代償は、ALIF 資格痕跡の正しさが完全に自前の責任になることです——そしてそれは、フェーズ 1 で最も外部の参照を必要とする部分です。§1.4／§八 が SpikingJelly を指定しているのも同じ方向の判断です。将来 OIOSL の条項が受け入れ難いほど厳しくなれば、これが最も低コストな退出経路です。

**B. 旧安定版 `spikingjelly==0.0.0.0.14` に固定し、Python 下限は動かさない。**

却下。当該版は 2023-03 公開で numpy 2 と torch 2.14 より前です。導入すれば import に失敗するか、torch も旧版に落とすことを強いられます——そして旧版の torch は RTX 5060 の sm_120 を支えません。これは「保守的」ではなく、本プロジェクトのハードウェアで動かない組み合わせに環境を釘付けにすることです。

**C. Apache/MIT ライセンスの SNN フレームワークに乗り換える。**

保留であり、却下ではありません。ライセンスと Python 下限の両方を同時に解決できますが、プロジェクト計画書の技術選定から外れ、§七 の三本の線のニューロン原始演算と代理勾配ベースラインをすべて照合し直す必要があります。**本 ADR はこの路線の実現可能性を評価していません**——OIOSL の商業利用開示義務が実際の障害になった時点で、新たな ADR で真剣に比較すべきです。

**D. 監査スクリプトはそのままにし、SpikingJelly のライセンスを文書に注記するだけにする。**

却下。これはまさに「検出できない隅」です——§12.3 がライセンス監査を CI の一項目に挙げているのは、人が覚えていることに依存しないためです。文書は漂流しますが、`--strict-unknown` は漂流しません。
