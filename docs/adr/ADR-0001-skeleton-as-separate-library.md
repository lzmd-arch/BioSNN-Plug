# ADR-0001：骨架库独立为 `biosnn-bus`

- **状态**：已采纳
- **日期**：2026-09-21
- **相关**：计划书 §七 第零阶段、§12.2 分层开源路线；[ADR-0002](ADR-0002-numpy-core-torch-optional.md)、[ADR-0004](ADR-0004-monorepo-uv-workspace.md)

## Context

计划书把整个项目压在一条高风险技术路线上：**完全放弃代理梯度**，用 e-prop +
核化 IB-Hebbian + R-STDP 三种纯局部规则组合出认知能力。计划书自己也承认这条路
"技术风险确实更高"（§十三），并且预留了多条降级路径（§十一）。

也就是说：**核心研究很可能失败或大幅降级。**

与此同时，整条路线里有一块**不依赖研究成败**的部分：模态插件的接口契约、注册与
发现机制、脉冲总线的接缝。无论 e-prop 能不能跑通、TAAF 能不能对齐模态，这部分
都要有，而且它的价值与学习规则的成败无关。

如果把它和认知核心写在同一个包里，就会连带承担研究代码的全部风险：API 反复变动、
依赖越来越重、`pip install` 装进来一堆用不上的东西。

## Decision

把插件框架抽成**独立分发包** `biosnn-bus`，放在 `packages/biosnn-bus/`：

- 它**不 import** 认知核心、学习规则、任何神经元模型；
- 它有自己的版本号、自己的测试、自己的 README；
- 它先于任何研究成果对外可用。

计划书 §12.2 把这条原则写成一句话：**研究可以失败，骨架必须可用。**

## Consequences

**好处**

- 研究代码可以随便改，不会波及骨架库的 API 承诺；
- `pip install biosnn-bus` 只拉 numpy，与"无 GPU 依赖、Colab 可跑"的硬性成功标准一致；
- 在研究成果出来之前就能积累用户、信誉与外部 review——计划书 §12.6 把"被同行论文
  当作 baseline 或工具引用"定义为比 star 数更真实的成功度量，而这条路只在骨架库
  存在时才走得通。

**代价（已接受）**

- 多一层抽象：认知核心要用插件，得经过 `SpikeBus` 这道接口。有些实验会想直接拿到
  原始脉冲数据，绕过总线更省事——**这种绕过是被允许的**，插件接口不强制走总线；
- 维护两个版本号、两个 README。见 [ADR-0005](ADR-0005-versioning-policy.md)；
- 骨架库有独立 CI，构建时间略增。

**没有解决的**

- 骨架库的接口设计得好不好，只能靠外部使用者来证伪。目前尚无外部使用者——
  这是计划书 §12.6 第 8 个月指标要回答的问题，不是本 ADR 能解决的。

## Alternatives

**A. 单包，插件框架作为子模块。**
否决。这样 `pip install biosnn-plug` 会拖入 torch、实验依赖和一堆研究中途废弃的
代码，与"5 分钟内跑通 Colab 演示"直接冲突。

**B. 先写研究代码，等接口稳定了再抽库。**
否决。这是最常见的顺序，但它把"必须先有骨架"这个前提反过来了。计划书 §12.2 的
判断是：骨架库不需要任何研究先成功，却能在研究成功之前积累用户与外部眼睛。
等研究做完再抽，等于放弃了这几年本该积累的东西。

**C. 干脆不做骨架库，全力冲研究。**
否决。理由同上，而且计划书 §12.6 的硬性指标（第 2 个月骨架库 `pip install` 可用、
CI 全绿）会直接落空。
