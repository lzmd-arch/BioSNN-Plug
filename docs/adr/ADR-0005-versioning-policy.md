# ADR-0005：版本策略——骨架库 semver，研究代码 12 个月免责期

- **状态**：已采纳
- **日期**：2026-09-21
- **相关**：计划书 §七 第零阶段任务 5、§12.2、§12.5；[ADR-0001](ADR-0001-skeleton-as-separate-library.md)、[ADR-0004](ADR-0004-monorepo-uv-workspace.md)

## Context

计划书 §12.5 有一句听起来很刺耳但很诚实的话：

> **响应预期管理**：单人维护，issue 响应不设 SLA，在 README 明示——管理预期比
> 假装有团队更利于社区信任。

同样的诚实要应用到 API 稳定性上。一个 36 个月的研究项目，前 12 个月会不断推翻
自己的设计：接口会因为实验需要而变形，目录会重组，今天觉得优雅的抽象明天可能
被证明是错的。

对**全部**代码承诺 API 稳定在这样一个研究项目里做不到（否决理由见 Alternatives A）。

但骨架库是另一回事：它的存在意义就是被别人依赖（[ADR-0001](ADR-0001-skeleton-as-separate-library.md)）。
一个今天能用、明天就 break 的库，没人会拿它写插件。计划书 §12.6 的"第 8 个月：
骨架库被非作者项目 import ≥ 1"这条硬性指标，前提就是 API 稳定。

## Decision

**两层策略，写进文档、写进 CI：**

### 骨架库 `biosnn-bus` —— 严格 semver

- 主版本号变化才允许破坏性变更；
- 0.x 阶段（当前是 `0.1.0`）：按 semver 约定，0.x 的次版本号（`0.1` → `0.2`）
  允许破坏性变更。**这是刻意的**——骨架库还没被外部依赖，此时快速迭代比假装稳定
  更有价值。第一个被外部依赖的版本发布时升到 `1.0.0`，从此严格遵守；
- `scripts/check_version_consistency.py` 在 CI 里保证 `pyproject.toml` 与
  `__init__.py` 的版本号永远一致——装到的版本和运行时自报的版本对不上，
  是排查 bug 时最浪费时间的一类问题。

### 研究代码 `research/` —— 12 个月破坏性变更免责期

- 头 12 个月内 API 不稳定，**不做任何兼容性承诺**；
- 不参与版本号一致性检查；
- 每个模块的 docstring 顶部标注免责期与到期日期。

### 计划书文档 —— 文件名与正文版本号必须一致

计划书 §12.3 点名要拦"文件名与内容版本号错位"：读者按文件名找 v6，拿到的却是 v6.2
的内容。

## Consequences

**好处**

- 贡献者知道哪些 API 可以放心依赖（骨架库），哪些不要依赖（研究代码）；
- 骨架库在 0.x 阶段能快速迭代，不为一个还没有用户的外部依赖付代价；
- 版本号一致性由 CI 保证，不靠自觉。

**代价（已接受）**

- 0.x 阶段仍可能 break，早期采用者要有心理准备。README 明示这一点；
- 研究代码的免责期意味着**这个阶段的成果很难被第三方直接复用**。这正是计划书
  §12.2 把"参考实现层"排在第 4-8 个月的原因——先让可复用的部分稳定下来，
  再放开研究代码。

**到期后怎么办**

12 个月免责期结束时（预计 2027-09），research 代码要么被重构进骨架库成为稳定 API，
要么被标注为"实验性，无兼容承诺"。**这篇 ADR 到期需要复审。**

## Alternatives

**A. 对全部代码承诺 semver。**
否决。要么绑住手脚（研究阶段的自我审查成本极高），要么违背承诺（更糟）。

**B. 完全不承诺任何稳定性。**
否决。骨架库的存在意义就是被依赖。没有稳定性承诺，计划书 §12.6 的"被非作者项目
import ≥ 1"不可能达成。

**C. 研究代码也纳入版本号一致性检查。**
否决。研究代码会以实验为单位快速增删，强制版本号纪律的收益远小于摩擦。

**D. 一开始就发 1.0.0 表示稳定。**
否决。0.x 是 Python 生态里表达"可以变"的标准方式，而我们现在确实会变。
提前发 1.0 只是在骗使用者。
