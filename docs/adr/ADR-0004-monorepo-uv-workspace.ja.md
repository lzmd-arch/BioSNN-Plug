# ADR-0004：monorepo + uv workspace を採用し、二リポジトリにはしない

[中文](ADR-0004-monorepo-uv-workspace.md) · [English](ADR-0004-monorepo-uv-workspace.en.md)

- **ステータス**：承認済み
- **日付**：2026-09-21
- **関連**：プロジェクト計画書 §12.2 段階的オープンソース化路線；[ADR-0001](ADR-0001-skeleton-as-separate-library.ja.md)、[ADR-0005](ADR-0005-versioning-policy.ja.md)

## Context

[ADR-0001](ADR-0001-skeleton-as-separate-library.ja.md) はスケルトンライブラリを独立した
配布パッケージとして切り出すことを決定しました。「独立した配布パッケージ」は「独立した
リポジトリ」と同じではありません——これは 2 つの別個の事柄であり、混同しやすいものです。

プロジェクト計画書 §12.2 の段階的オープンソース化路線には「スケルトンライブラリ
（biosnn-bus）を先行してオープンソース化する」と書かれており、字面だけを見れば
二リポジトリに近いものです。しかしプロジェクト計画書は同時に、本プロジェクトが
**単独メンテナンス**であることを明示しています（§12.5：issue への応答に SLA を設けず、
そのことを README に明示する）。

単独メンテナンスがここでの決定的な制約です。二リポジトリは次を意味します：
CI が 2 系統、コミットが 2 回、issue キューが 2 つ、そして最も厄介なもの——
**リポジトリ横断の変更**です。スケルトンライブラリのインターフェースを 1 つ変えれば
研究コードも追随して変わり、PR を 2 つ出し、CI を 2 回待ち、両側で commit hash を
相互に参照することになります。

## Decision

**単一リポジトリの monorepo** とし、スケルトンライブラリをサブパッケージとします：

```text
BioSNN-Plug/
├─ packages/biosnn-bus/    独立した配布パッケージ：独立した pyproject、独立したバージョン番号、独立したテスト
├─ research/               研究コード（第 1 フェーズ以降）
└─ docs/  examples/  scripts/
```

**uv workspace** で管理します：ルートの `pyproject.toml` がメンバーを宣言し、`uv sync`
の 1 コマンドで開発環境が整い、スケルトンライブラリは editable インストールとなるため、
コードを変えると即座に反映されます。

重要な点：**それでも独立してリリースできる配布パッケージです**。
`uv build --package biosnn-bus` が生成する wheel は、独立したリポジトリからビルドした
ものと完全に同一であり、単独で PyPI にリリースできます。リポジトリの形態と配布の形態は
分離しています。

## Consequences

**利点**

- 1 回のコミットでスケルトンライブラリと研究コードを同時に変更でき、CI は 1 回で
  完了します；
- issue キューが 1 つ、ガバナンス文書が 1 セットで済みます；
- `uv sync` の 1 コマンドで開発依存関係がすべて入ります；
- スケルトンライブラリの「独立性」を保証するのは**依存グラフ**（認知コアを import せず、
  wheel をインストールした後に torch が入っていないことを CI でアサートします）であり、
  ディレクトリの位置ではありません——後者は形式であり、前者が実質です。

**コスト（受け入れ済み）**

- スケルトンライブラリだけを気にする人にとって、リポジトリは肥大して見えます。
  `packages/biosnn-bus/README.md` が PyPI にリリースされる README と独立していることが、
  この点を緩和しています；
- スケルトンライブラリの CI と研究コードの CI が同じ workflow の中にあります。現在は
  job で分離していますが、将来研究コードの CI が非常に重くなった場合（GPU テスト、
  長時間の学習）、パスフィルタを追加する必要があります；
- 将来、活発なサードパーティのメンテナが本当に現れた場合、スケルトンライブラリを
  切り出す必要があるかもしれません。**そのときに切り出します**——分割は再統合より
  はるかに容易です。

**解決していないこと**

- GitHub のコントリビュータ統計やスター数はリポジトリ単位で集計されるため、スケルトン
  ライブラリはこれらの指標を独立に積み上げることができません。プロジェクト計画書
  §12.6 が「同分野の論文から引用されること」の方がスター数より真実味があると明言して
  いることを踏まえると、この損失は受け入れ可能です。

## Alternatives

**A. 二リポジトリ：`biosnn-bus` と `BioSNN-Plug` を分ける。**
却下（現段階）。単独メンテナンスの下では、リポジトリ横断の変更の摩擦が実際に開発を
遅らせますし、それと引き換えに得られる「スケルトンライブラリを先行してオープンソース
化する」という語りの効果は、monorepo のサブパッケージでも同じように達成できます。
**この決定は撤回できます**：`packages/biosnn-bus/` ディレクトリ自体が完全にリリース
可能なパッケージであり、実際に切り出すときは `git subtree split` で済み、履歴もそのまま
持っていけます。

**B. 単一リポジトリとしつつ、スケルトンライブラリを独立にパッケージングしない（`biosnn_bus/` を直接最上位に置く）。**
却下。それは [ADR-0001](ADR-0001-skeleton-as-separate-library.ja.md) が却下した案に戻る
ことになります：独立にリリースできず、外部のユーザーはインストールできません。

**C. git submodule でスケルトンライブラリをぶら下げる。**
却下。submodule の日常的な操作（ポインタの更新、detach HEAD、`--init` の付け忘れ）は
コントリビュータにとって純粋な摩擦であり、得られるものは「二リポジトリのように
見える」ことだけです。
