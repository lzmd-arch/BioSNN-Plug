# ADR-0001：スケルトンライブラリを `biosnn-bus` として独立させる

[中文](ADR-0001-skeleton-as-separate-library.md) · [English](ADR-0001-skeleton-as-separate-library.en.md)

- **ステータス**：承認済み
- **日付**：2026-09-21
- **関連**：プロジェクト計画書 §七 第 0 フェーズ、§12.2 階層的なオープンソース路線；[ADR-0002](ADR-0002-numpy-core-torch-optional.ja.md)、[ADR-0004](ADR-0004-monorepo-uv-workspace.ja.md)

## Context

プロジェクト計画書はプロジェクト全体を 1 本の高リスクな技術路線に賭けています：
**代理勾配を完全に放棄**し、e-prop + カーネル化 IB-Hebbian + R-STDP という 3 つの
純粋に局所的な学習則の組み合わせで認知能力を作り出そうというものです。プロジェクト
計画書自身もこの路線は「技術リスクが確かに高い」（§十三）と認めており、複数の縮退パス
（§十一）を用意しています。

つまり：**中核となる研究は失敗するか、大きく縮退する公算が高いということです。**

一方で、この路線全体の中には**研究の成否に依存しない**部分があります：モダリティ
プラグインのインターフェースコントラクト、登録と発見のメカニズム、スパイクバスの
継ぎ目です。e-prop が動作するかどうか、TAAF がモダリティを整列できるかどうかに
関わらず、この部分は必要であり、しかもその価値は学習則の成否とは無関係です。

これを認知コアと同じパッケージに書いてしまうと、研究コードのリスクを丸ごと抱え込む
ことになります：API が繰り返し変わり、依存関係がどんどん重くなり、`pip install` で
使わないものが大量に入ってきます。

## Decision

プラグインフレームワークを**独立した配布パッケージ** `biosnn-bus` として切り出し、
`packages/biosnn-bus/` に置きます：

- 認知コア、学習則、いかなるニューロンモデルも**import しません**；
- 独自のバージョン番号、独自のテスト、独自の README を持ちます；
- いかなる研究成果よりも先に、外部から利用可能になります。

プロジェクト計画書 §12.2 はこの原則を一文にしています：**研究は失敗してよいが、
スケルトンライブラリは使えなければならない。**

## Consequences

**利点**

- 研究コードは自由に変更でき、スケルトンライブラリの API の約束に影響しません；
- `pip install biosnn-bus` が引っ張るのは numpy だけで、「GPU 依存なし、Colab で動作」と
  いうハードな成功基準と一致します；
- 研究成果が出る前にユーザー、信用、外部レビューを積み上げられます——プロジェクト
  計画書 §12.6 は「同分野の論文からベースラインやツールとして引用されること」を
  スター数よりも真実味のある成功の尺度と定義しており、その道はスケルトンライブラリが
  存在して初めて開けます。

**コスト（受け入れ済み）**

- 抽象が 1 層増えます：認知コアがプラグインを使うには、`SpikeBus` というインターフェースを
  通らなければなりません。生のスパイクデータを直接取りたい実験もあり、バスを迂回する方が
  手間が少なくて済みます——**この迂回は許可されています**。プラグインインターフェースは
  バスの経由を強制しません；
- バージョン番号 2 つと README 2 つを維持することになります。詳しくは
  [ADR-0005](ADR-0005-versioning-policy.ja.md) を参照；
- スケルトンライブラリは独立した CI を持ち、ビルド時間がわずかに増えます。

**解決していないこと**

- スケルトンライブラリのインターフェース設計が良いかどうかは、外部の利用者によって
  反証されるしかありません。現時点で外部利用者は存在しません——これはプロジェクト
  計画書 §12.6 の 8 か月目の指標が答えるべき問いであり、本 ADR が解決できるものでは
  ありません。

## Alternatives

**A. 単一パッケージとし、プラグインフレームワークをサブモジュールにする。**
却下。そうすると `pip install biosnn-plug` が torch、実験用の依存関係、研究中に途中で
捨てられたコードを大量に引き込むことになり、「5 分以内に Colab デモを動かす」と
真っ向から衝突します。

**B. 先に研究コードを書き、インターフェースが安定してからライブラリを切り出す。**
却下。これは最もよくある順序ですが、「先にスケルトンライブラリがなければならない」
という前提を逆にしています。プロジェクト計画書 §12.2 の判断はこうです：スケルトン
ライブラリは研究が先に成功することを必要としないが、研究が成功する前にユーザーと
外部の目を積み上げることができる。研究が終わってから切り出すのでは、この数年間に
積み上げられたはずのものを放棄することになります。

**C. スケルトンライブラリを作らず、研究に全力を注ぐ。**
却下。理由は上と同じであり、しかもプロジェクト計画書 §12.6 のハードな指標（2 か月目に
スケルトンライブラリが `pip install` で利用可能、CI がすべてグリーン）が直接達成できなく
なります。
