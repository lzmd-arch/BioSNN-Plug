# ADR-0003：プラグインの発見はグローバルレジストリではなくエントリポイントで行う

[中文](ADR-0003-entry-point-plugin-discovery.md) · [English](ADR-0003-entry-point-plugin-discovery.en.md)

- **ステータス**：承認済み
- **日付**：2026-09-21
- **関連**：プロジェクト計画書 §1.2 中核目標 2、§12.6 オープンソース成功指標；[ADR-0001](ADR-0001-skeleton-as-separate-library.ja.md)

## Context

プロジェクト計画書 §1.2 は「**モダリティの追加に既存アーキテクチャの変更を要さない**」を
中核目標の一つに挙げ、§12.6 はそれを測定可能な指標に落とし込んでいます：24 か月目に
「外部から貢献されたモダリティプラグイン ≥ 1」（有機的な目標）、36 か月目に
「サードパーティプラグインのエコシステムが形成される」（ビジョン）。

この 2 つが成立する前提は、**他人が書いたモダリティプラグインが本リポジトリに PR を
出す必要がないこと**です。モダリティを 1 つ追加するたびに `biosnn_bus` のソースを
書き換えなければならないのなら、それはプラグイン化ではなく「メインリポジトリに
コードを押し込むこと」です。

したがって本当の問題は「どうやってプラグインを登録するか」ではなく、「**独立した
サードパーティパッケージをどうやって本ライブラリに見つけさせるか**」です。

同時に第 2 の制約もあります：プロジェクト計画書 §七 第 0 フェーズの成功基準は
「カスタムモダリティプラグインの登録」のデモを要求しており、ユーザーが自分の
スクリプト内でプラグインを定義して即座に使う——この経路も短くなければなりません。

## Decision

**2 つの経路が併存します**：

1. **プロセス内登録**：`@register_plugin("name")` デコレータで、モジュールレベルの
   グローバルレジストリに書き込みます。同一リポジトリ内のプラグインと対話的な探索に
   適しており、最短の経路です。
2. **エントリポイントによる発見**：`discover_plugins()` が
   `importlib.metadata.entry_points(group="biosnn_bus.plugins")` で、インストール済みの
   サードパーティ配布パッケージを走査します。

サードパーティパッケージの組み込み方：

```toml
# サードパーティパッケージ自身の pyproject.toml —— BioSNN-Plug のコードは 1 行も触る必要がありません
[project.entry-points."biosnn_bus.plugins"]
audio = "my_pkg.plugins.audio:AudioPlugin"
```

`discover_plugins()` は**冪等**であり、登録済みの同名エントリはスキップされるため、
安心して繰り返し呼び出せます。あるエントリポイントが指す先が `ModalityPlugin` の
サブクラスでない場合、または読み込み時に ImportError を送出した場合、エラーメッセージ
にはそのエントリポイントの名前と value が含まれます——サードパーティパッケージの
インポート失敗が「プラグインが理由もなく消えた」という形で現れてはなりません。

## Consequences

**利点**

- サードパーティプラグインは**完全に独立**しています：自身のリポジトリ、自身の CI、
  自身のリリースサイクル。本リポジトリの変更はゼロです；
- Python のパッケージングエコシステムの利点（バージョン制約、依存関係の解決、
  プライベートインデックスからの配布）をそのまま得られます；
- グローバルレジストリとエントリポイントの組み合わせにより、2 つの経路が同じ検索
  ロジック（`get_plugin`）を共有します。ユーザーはプラグインがどこから来たのかを
  知る必要がありません。

**コスト（受け入れ済み）**

- **グローバルな可変状態**：モジュールレベルのレジストリはプロセス単位です。テスト間
  では分離が必要です（`packages/biosnn-bus/tests/conftest.py` の `isolated_registry`
  フィクスチャを参照）。そうしなければ、あるテストが登録したプラグインが次のテストに
  漏れ出します。これは実在する落とし穴であり、テスト用フィクスチャ側で対処済みです；
- 名前の衝突は既定でエラーになり、暗黙に上書きされません（上書きされるのは
  `override=True` の場合だけです）。2 つのモダリティプラグインが同名になったとき、
  開発者は登録したその瞬間に気づきます。学習の途中になって、使っているのが他人の
  エンコーダだと気づくのではなく；
- デコレータ `@register_plugin` は**インポートの副作用**です——プラグインモジュールを
  import しなければ登録されません。これは Python プラグインでは標準的なやり方であり、
  `get_plugin` のエラーメッセージでは `discover_plugins()` を特に案内しています。

**解決していないこと**

- プラグインのバージョン互換性チェックはありません。サードパーティプラグインが要求として
  `biosnn-bus>=0.1` を宣言すればそれで十分であり、スケルトンライブラリはプラグインが
  実際にどのバージョンの API を使っているかを検証しません。実際にサードパーティ
  プラグインが現れてから考えることにします。

## Alternatives

**A. デコレータによるグローバルレジストリのみを実装する。**
却下。これでは「サードパーティプラグイン」が本ライブラリを `import` したうえでさらに
import される必要があり、独立した配布の可能性を事実上排除してしまいます
——コミュニティのメンバーは PR を出すしかなくなり、これはまさに避けようとしていた
状況です。

**B. エントリポイントのみを実装する。**
却下。すぐに使えるプラグインを 1 つ書くにも、まずパッケージを作ってインストールしなければ
ならず、対話的な探索にもサンプルのデモにも煩雑すぎます。プロジェクト計画書 §七
第 0 フェーズが求めているのは、まさに「5 分でプラグインを 1 つ登録する」という
短い経路です。

**C. プラグインが設定ファイル（YAML/JSON）でパスを宣言する。**
却下。Python のパッケージングと依存関係管理を迂回することになり、ユーザー自身が
依存関係のインストール済みとパスの一致を保証しなければならず、しかも静的チェック
ツールからはこれらの文字列がまったく見えません。

**D. `pluggy`（pytest のプラグインシステム）のような既存のプラグインフレームワークを使う。**
却下（現段階）。実行時依存が 1 つ増える一方で、必要なのは「名前からクラスを探す」という
能力 1 つだけであり、`importlib.metadata` は標準ライブラリです。複雑なフックの要求が
実際に現れたときに再評価します。
