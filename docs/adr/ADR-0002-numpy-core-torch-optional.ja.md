# ADR-0002：スケルトンライブラリのコアは numpy、torch はオプションのブリッジ

[中文](ADR-0002-numpy-core-torch-optional.md) · [English](ADR-0002-numpy-core-torch-optional.en.md)

- **ステータス**：承認済み
- **日付**：2026-09-21
- **関連**：プロジェクト計画書 §七 第 0 フェーズの成功基準、§1.4 の技術的制約；[ADR-0001](ADR-0001-skeleton-as-separate-library.ja.md)

## Context

プロジェクト計画書 §七 がスケルトンライブラリに対して定めたハードな成功基準には、
次の一項があります：

> Colab の **GPU なし**環境でデモが動作すること。

一方、プロジェクト計画書 §1.4 と §八 の技術選定表は、プロジェクト全体の技術スタックを
**SpikingJelly + PyTorch + eprop-PyTorch** と定めています。認知コアが torch を使うことは
疑いありません。

問題は、スケルトンライブラリもそれに追随するかどうかです。

`torch` の wheel は約 2GB あります（CUDA 版）。`pip install biosnn-bus` がこれを
引き込むとすれば、次のようになります：

- モダリティプラグインを書きたいだけの人が 2GB をダウンロードすることになる；
- Colab で `pip install` が数分待たされ、「5 分でデモを動かす」は即座に破綻する；
- スケルトンライブラリは「独立した軽量ライブラリ」という位置づけと自ら矛盾する。

さらに見えにくい問題があります：プロジェクト計画書 §2.3 のインターフェース仕様には
こう書かれています：

```python no-run
@abstractmethod
def get_membrane(self) -> nn.Module: ...
```

`nn.Module` は torch の型です。シグネチャにこれを書く限り、スケルトンライブラリは
`import torch` せざるを得ず、依存は避けられません。

## Decision

**スケルトンライブラリのコアは numpy だけに依存します。**

1. `SpikeTrain` は内部に numpy 配列を保持し、バックエンドに依存しません。torch テンソルは
   `SpikeTrain.to_torch()` / `SpikeTrain.from_torch()` でブリッジし、実装はオプションの extra
   `biosnn-bus[torch]` の下に置き、import を遅延させます。
2. `get_membrane` の戻り値の型を `nn.Module` から構造的プロトコル
   [`Membrane`](../../packages/biosnn-bus/src/biosnn_bus/types.py) に変更します——要求するのは
   `forward` メソッドが存在することだけです。認知コアが返す `nn.Module` のサブクラスは
   **構造的に自動で**このプロトコルを満たし、プラグイン作者の書き方は影響を受けません。
   詳しくは [ADR-0006](ADR-0006-plugin-interface-fidelity.ja.md) を参照。
3. CI で明示的にアサートします：クリーンな venv に wheel をインストールした後、`torch` が
   **存在しない**こと。

## Consequences

**利点**

- `pip install biosnn-bus` が引っ張るのは numpy だけで、秒単位で完了する；
- Colab のデモは GPU も待ち時間も不要で、第 0 フェーズのハードな基準を直接満たす；
- スケルトンライブラリはどの Python 環境でもテストでき、CI マトリクスで 3.10/3.11/3.12 を
  回すのはまったく苦にならない；
- 逆に、よい結果を強制されます：インターフェースは**必ず**特定のテンソルライブラリから
  切り離されます。将来 JAX に替えるにせよ、Loihi/Lava に直接接続するにせよ、
  インターフェースを変える必要はありません。

**コスト（受け入れ済み）**

- ライブラリをまたいでデータを渡すときは明示的な変換（`.to_torch()`）が必要で、テンソルを
  そのまま渡すより一手間多い；
- `Membrane` プロトコルは構造的型なので、`isinstance` による検査は `forward` の有無しか
  見ず、シグネチャの不一致は捉えられません。これは Python の Protocol の本質的な制限です；
- バス内の数値演算は numpy 上で走るため、torch より遅くなります。スケルトンのフェーズでは
  データ量が少なく、許容できます；実際にボトルネックになったときは、認知コア側が
  `SpikeBus` を迂回して生の `SpikeTrain` を直接取れます。

**明確な非目標**

- スケルトンライブラリは軽量な SNN シミュレータでは**ありません**。ニューロンダイナミクスも
  学習則も扱いません。それらは認知コアと SpikingJelly の仕事です。

## Alternatives

**A. コアが torch に依存する。**
却下。第 0 フェーズのハードな成功基準に直接違反し、しかも 2GB のインストールサイズは
「独立した軽量ライブラリ」という位置づけと衝突します。

**B. コアはどの配列ライブラリにも依存せず、純粋な Python の list を使う。**
却下。スパイクデータは `(T, N)` の密な配列であり、純粋な Python ではデモができないほど
遅くなり、しかも numpy 自体は十数 MB しかなく、負担になりません。

**C. `array-api-compat` でバックエンド非依存の抽象化を行う。**
却下（現段階）。これが解くのは「numpy/torch/jax を同時にサポートする」問題であり、
こちらに必要なのは「コアは numpy、境界で torch をブリッジする」ことだけです。抽象を
1 層増やしても実際の利益は得られず、本当にマルチバックエンドが必要になったときに
導入すれば遅くありません。
