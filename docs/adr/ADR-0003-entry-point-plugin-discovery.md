# ADR-0003：插件发现用 entry points，而非全局注册表

- **状态**：已采纳
- **日期**：2026-09-21
- **相关**：计划书 §1.2 核心目标 2、§12.6 开源成功指标；[ADR-0001](ADR-0001-skeleton-as-separate-library.md)

## Context

计划书 §1.2 把"**新增模态无需修改已有架构**"列为核心目标之一，§12.6 又把它落到
一个可测的指标上：第 24 个月"外部贡献的模态插件 ≥ 1"（有机目标），第 36 个月
"第三方插件生态形成"（愿景）。

这两条要成立，前提是**别人写的模态插件不需要往本仓库提 PR**。如果每加一个模态都要
改 `biosnn_bus` 的源码，那就不叫插件化，叫"往主仓库塞代码"。

所以真正的问题不是"怎么注册插件"，而是"**怎么让一个独立的第三方包被本库发现**"。

同时还有第二个约束：计划书 §七 第零阶段的成功标准要求演示"注册自定义模态插件"，
用户在自己的脚本里定义插件、立刻使用——这条路也要短。

## Decision

**两条通道并存**：

1. **进程内注册**：`@register_plugin("name")` 装饰器，写入模块级全局注册表。
   适合同仓库插件与交互式探索，最短路径。
2. **entry points 发现**：`discover_plugins()` 用
   `importlib.metadata.entry_points(group="biosnn_bus.plugins")` 扫描已安装的
   第三方分发包。

第三方包的接入方式：

```toml
# 第三方包自己的 pyproject.toml —— 不需要碰 BioSNN-Plug 任何一行代码
[project.entry-points."biosnn_bus.plugins"]
audio = "my_pkg.plugins.audio:AudioPlugin"
```

`discover_plugins()` 是**幂等**的，已注册的同名条目会被跳过，因此可以放心重复调用。
若某个 entry point 指向的不是 `ModalityPlugin` 子类，或者加载时抛 ImportError，
错误信息里会带上 entry point 的名字与 value——第三方包的导入失败不应该表现为
"插件莫名不见了"。

## Consequences

**好处**

- 第三方插件**完全独立**：自己的仓库、自己的 CI、自己的发布节奏。本仓库零改动；
- 自动获得 Python 打包生态的全部好处（版本约束、依赖解析、私服分发）；
- 全局注册表 + entry points 的组合让两条路径共享同一套查找逻辑（`get_plugin`），
  用户不需要知道插件从哪来。

**代价（已接受）**

- **全局可变状态**：模块级注册表是进程级的。测试之间必须隔离（见
  `packages/biosnn-bus/tests/conftest.py` 里的 `isolated_registry` 夹具），否则一个
  测试注册的插件会泄漏到下一个测试。这是真实存在的坑，已经在测试夹具里处理；
- 重名冲突默认报错而非静默覆盖（`override=True` 才覆盖）。两个模态插件撞名时，
  开发者在注册那一刻就知道，而不是训练到一半发现用的是别人的编码器；
- 装饰器 `@register_plugin` 是**导入副作用**——不 import 插件模块就不会注册。
  这是 Python 插件的通行做法，`get_plugin` 的报错信息里专门提示了
  `discover_plugins()`。

**没有解决的**

- 没有插件版本兼容性检查。第三方插件声明要求 `biosnn-bus>=0.1` 就够了，
  骨架库不会去校验插件实际用了哪个版本的 API。等真有第三方插件时再说。

## Alternatives

**A. 只做装饰器全局注册表。**
否决。它让"第三方插件"必须 `import` 本库再被 import 到，实际上排除了独立分发的
可能——社区成员只能提 PR，正是要避免的局面。

**B. 只做 entry points。**
否决。写一个即时可用的插件也要先建包、装包，交互式探索与示例演示都太笨重。
计划书 §七 第零阶段要的正是"5 分钟注册一个插件"的短路径。

**C. 插件通过配置文件（YAML/JSON）声明路径。**
否决。绕开了 Python 的打包与依赖管理，用户要自己保证依赖装好了、路径对得上，
而且静态检查工具完全看不见这些字符串。

**D. 用 `pluggy`（pytest 的插件系统）之类的现成插件框架。**
否决（现阶段）。多一个运行时依赖，而我们只需要"按名字找类"这一个能力，
`importlib.metadata` 是标准库。真出现复杂的 hook 需求时再评估。
