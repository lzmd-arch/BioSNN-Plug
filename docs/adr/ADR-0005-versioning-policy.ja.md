# ADR-0005：バージョン方針——スケルトンライブラリは semver、研究コードは 12 か月の免責期間

[中文](ADR-0005-versioning-policy.md) · [English](ADR-0005-versioning-policy.en.md)

- **ステータス**：承認済み
- **日付**：2026-09-21
- **関連**：プロジェクト計画書 §七 第 0 フェーズのタスク 5、§12.2、§12.5；[ADR-0001](ADR-0001-skeleton-as-separate-library.ja.md)、[ADR-0004](ADR-0004-monorepo-uv-workspace.ja.md)

## Context

プロジェクト計画書 §12.5 に、耳が痛いが正直な一文があります：

> **応答に関する期待値の管理**：メンテナは 1 名で、issue への応答に SLA を設けず、
> README に明示します——チームがあるように装うよりも、期待値を管理するほうが
> コミュニティの信頼につながります。

同じ正直さを API の安定性にも適用します。36 か月の研究プロジェクトでは、最初の
12 か月に自分の設計を何度も覆すことになります：インターフェースは実験の必要に
応じて変形し、ディレクトリは再編成され、今日エレガントだと思っていた抽象が
明日には誤りだと証明されるかもしれません。

**すべての**コードに対して API の安定を約束することは、このような研究プロジェクトでは
できません（却下理由は Alternatives A を参照）。

しかしスケルトンライブラリは別です：その存在意義は他者から依存されることそのものに
あります（[ADR-0001](ADR-0001-skeleton-as-separate-library.ja.md)）。
今日は使えて明日には break するライブラリを、プラグインを書くのに使おうという人は
いません。プロジェクト計画書 §12.6 の「8 か月目：スケルトンライブラリが非作者の
プロジェクトから import される ≥ 1」というハードな指標も、その前提が API の安定です。

## Decision

**二層の方針を、ドキュメントに書き、CI にも書き込みます：**

### スケルトンライブラリ `biosnn-bus` —— 厳格な semver

- 破壊的変更が許されるのはメジャーバージョンが変わるときだけです；
- 0.x の段階（現在は `0.1.0`）：semver の取り決めでは、0.x のマイナーバージョン
  （`0.1` → `0.2`）に破壊的変更を入れられます。**これは意図的なものです**——
  スケルトンライブラリはまだ外部から依存されておらず、この時期は安定しているふりを
  するよりも素早く反復するほうに価値があります。外部から依存される最初のバージョンを
  リリースするときに `1.0.0` に上げ、それ以降は厳格に守ります；
- `scripts/check_version_consistency.py` が CI で `pyproject.toml` と
  `__init__.py` のバージョン番号が常に一致することを保証します——インストールされた
  バージョンと実行時に自己申告されるバージョンが食い違うのは、バグを調べるときに
  最も時間を浪費する類の問題です。

### 研究コード `research/` —— 12 か月の破壊的変更免責期間

- 最初の 12 か月間は API が不安定で、**互換性について一切約束しません**；
- バージョン番号の一致性チェックには参加しません；
- 各モジュールの docstring の先頭に、免責期間と満了日を明記します。

### プロジェクト計画書ドキュメント —— ファイル名と本文のバージョン番号の一致

プロジェクト計画書 §12.3 は「ファイル名と内容のバージョン番号のずれ」を名指しで
防ぐ対象にしています：読者がファイル名から v6 を探して開いたのに、手に入るのは
v6.2 の中身です。

## Consequences

**利点**

- コントリビュータは、どの API を安心して依存してよいか（スケルトンライブラリ）、
  どれを依存すべきでないか（研究コード）が分かります；
- スケルトンライブラリは 0.x の段階で素早く反復でき、まだユーザーのいない外部依存の
  ためにコストを払わずに済みます；
- バージョン番号の一致性は CI が保証し、各自の心がけには頼りません。

**コスト（受け入れ済み）**

- 0.x の段階では依然として break し得るので、早期採用者には心の準備が必要です。
  README にこの点を明示します；
- 研究コードの免責期間は、**このフェーズの成果がサードパーティに直接再利用されにくい**
  ことを意味します。これこそプロジェクト計画書 §12.2 が「リファレンス実装層」を
  第 4-8 か月に置いている理由です——先に再利用可能な部分を安定させ、そのうえで
  研究コードを開放します。

**満了後はどうするか**

12 か月の免責期間が終わるとき（2027-09 予定）、research コードはスケルトンライブラリに
リファクタリングして安定した API にするか、そうでなければ「実験的、互換性の約束なし」と
明示するかのどちらかです。**本 ADR は満了時に見直しが必要です。**

## Alternatives

**A. すべてのコードに対して semver を約束する。**
却下。手足を縛ることになるか（研究フェーズの自己検閲コストは極めて高い）、約束を
破ることになるか（こちらのほうが悪い）です。

**B. 安定性についていかなる約束もしない。**
却下。スケルトンライブラリの存在意義は依存されることそのものにあります。安定性の
約束がなければ、プロジェクト計画書 §12.6 の「非作者のプロジェクトから import
される ≥ 1」は達成できません。

**C. 研究コードもバージョン番号の一致性チェックに含める。**
却下。研究コードは実験単位で素早く追加・削除されるため、バージョン番号の規律を
強制する利得は摩擦を大きく下回ります。

**D. 最初から 1.0.0 を出して安定を示す。**
却下。0.x は Python エコシステムで「変わり得る」ことを表す標準的な方法であり、
そして現在、実際に変わります。1.0 を前倒しで出すのは、利用者を
騙すだけです。
