# ADR-0006：`ModalityPlugin` はプロジェクト計画書 §2.3 の元のシグネチャを維持

[中文](ADR-0006-plugin-interface-fidelity.md) · [English](ADR-0006-plugin-interface-fidelity.en.md)

- **ステータス**：承認済み
- **日付**：2026-09-21
- **関連**：プロジェクト計画書 §2.3 モダリティプラグインインターフェース仕様；[ADR-0002](ADR-0002-numpy-core-torch-optional.ja.md)

## Context

プロジェクト計画書 §2.3 は `ModalityPlugin` の完全なインターフェース定義を与えており、
3 つのメソッドと 2 つのプロパティ、および既定値を持つ 2 つのプロパティを含みます。
この仕様はプラグイン化設計全体の土台であり、プロジェクト計画書の中でも十分に具体的に
書かれていて、そのまま写せる数少ない部分でもあります。

しかし [ADR-0002](ADR-0002-numpy-core-torch-optional.ja.md) はスケルトンライブラリの
コアが torch に依存しないと決定しており、プロジェクト計画書の仕様には次の 1 行が
あります：

```python no-run
@abstractmethod
def get_membrane(self) -> nn.Module: ...
```

`nn.Module` は torch の型です。これをそのまま写すと、スケルトンライブラリは
`import torch` せざるを得ません。

ここで実際のトレードオフが生じます：**インターフェースを変えるか、型ヒントを変えるか？**

## Decision

**シグネチャは一字も変えず、戻り値の型だけを構造的プロトコルに置き換えます。**

5 つのメンバーはすべてプロジェクト計画書の原文どおりに実装します：

| メンバー | プロジェクト計画書の原文 | スケルトンライブラリの実装 |
| :--- | :--- | :--- |
| `encode(raw_input)` | 抽象メソッド | 一致 |
| `get_membrane()` | 抽象メソッド、`nn.Module` を返す | `Membrane` プロトコルを返す（**唯一の逸脱**） |
| `decode(spike_output)` | 抽象メソッド | 一致 |
| `modality_name` | 抽象プロパティ | 一致 |
| `spike_dim` | 抽象プロパティ | 一致 |
| `temporal_scale` | 既定値 `10.0` | 一致 |
| `fusion_channel` | 既定値 `'temporal'` | 一致 |

`Membrane` は `runtime_checkable` な `Protocol` で、`forward` メソッドが存在すること
だけを要求します：

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Membrane(Protocol):
    def forward(self, x): ...
```

認知コアが返す `nn.Module` のサブクラスは、このプロトコルを**構造的に自動で満たします**
——`nn.Module` はもともとサブクラスに `forward` の実装を要求するからです。したがって
認知コアとプラグイン作者にとって、書き方はまったく変わりません。

さらに、プロジェクト計画書にないメンバーを 2 つ追加します。どちらも純粋な追加であり、
互換性に影響しません：

- `channel` プロパティ：`fusion_channel` の列挙形式で、バス内部で使用します。同時に
  検証の役割も担い、`fusion_channel` が不正な文字列を返したときはここでエラーに
  なります；
- `validate()` メソッド：インターフェースコントラクトのセルフチェック。
  `SpikeBus.register()` がこれを呼びます。

## Consequences

**利点**

- プロジェクト計画書のインターフェース仕様が引き続き対外コントラクトであり、計画書を
  読んでもコードを読んでも同じものが見えます；
- プラグイン作者はプロジェクト計画書どおりにコードを書けば動作し、Protocol と
  `nn.Module` の関係を理解する必要はありません；
- スケルトンライブラリは torch 依存ゼロを維持します。

**コスト（受け入れ済み）**

- **型チェックが弱くなります**：`Membrane` は構造的プロトコルなので、
  `isinstance(x, Membrane)` は `forward` プロパティの有無しか調べられず、シグネチャの
  不一致（たとえば `forward(self)` のように引数が 1 つ足りない場合）を捉えられません。
  これは Python Protocol の本質的な制限であり、本決定が持ち込んだものではありません；
- 厳密に言えばこれは**プロジェクト計画書からの 1 つの逸脱**であり、ただしごく小さい
  ものです。コードを読む人が `nn.Module` ではなく `Membrane` を見たとき、書き漏らし
  だと思うのではなく、ここに理由を見つけられるべきです。

**なぜ検証を `validate()` に置き、`__init_subclass__` に置かないのか**

プロジェクト計画書に関連する議論では、`__init_subclass__` で `spike_dim` などの制約を
検証することが想定されていました。これはできません：これらは**インスタンス属性**で
あり、クラス定義の時点では調べるべき値がまだありません。本当のタイミングは 2 つ——
インスタンス化の時か、登録の時です。登録の時（`SpikeBus.register` が `validate()` を
呼ぶ）を選んだのは、次の理由からです：

- ABC はサブクラスに `__init__` の実装を強制すべきではありません（多くのプラグインには
  不要です）；
- 登録はプラグインがシステムに入る唯一の入口であり、ここで遮断すれば網羅範囲が最も
  広く、エラーメッセージも最も文脈を持ちます（「どのバスが拒否したのか」を添えられます）。

## Alternatives

**A. プロジェクト計画書を厳密にそのまま写し、`get_membrane() -> nn.Module` とする。**
却下。[ADR-0002](ADR-0002-numpy-core-torch-optional.ja.md) に直接違反し、ひいては
第 0 フェーズの「Colab で GPU なしに動作する」というハードな成功基準にも違反します。

**B. `get_membrane` を削除し、膜電位は認知コア自身が管理する。**
却下。これはプロジェクト計画書のインターフェースに対する**実質的な**変更であり、型
レベルの調整ではありません。`get_membrane` は、プラグインが「このモダリティの
ニューロンがどういう形をしているか」を認知コアに晒す唯一の経路です；これを削除すると、
認知コアが逆に各モダリティの内部構造を知らなければならなくなり、プラグイン化の境界が
壊れます。

**C. 戻り値の型を `Any` と注釈する。**
却下。最も手間が省けるように見えて、実際には最悪です：型チェッカーが完全に役に立たなく
なり、読者もこの戻り値が何を満たすべきか分かりません。Protocol は少なくともコントラクト
を書き留めており、しかもそれは実行可能なドキュメントです。

**D. 独自の `Membrane` 抽象基底クラス（ABC）を定義し、プラグインに継承を要求する。**
却下。そうすると `nn.Module` のサブクラスを**そのまま**返せなくなり、認知コアが適応層を
書かなければならなくなります。構造的プロトコルの利点はまさに、明示的な継承を必要と
しない点にあります。
