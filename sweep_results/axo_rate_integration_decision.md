# 速率候选是否接进 Axo：决定记录

**日期：2026-10-18。** 速率路线结果见
[`axo_rate_candidate_validation_results.md`](axo_rate_candidate_validation_results.md)、
[`axo_rate_adaptive_results.md`](axo_rate_adaptive_results.md)。

## 结论

**不接。** 50k 的全局 W 补全候选（固定 M=15,000）在 Axo 里**没有用户路径消费者**；
接进去会是一段只有基准脚本会走的死代码。

## 消费审计

| 路径 | 实际扫描/计算 | 是否消费全局 W 候选 |
| :--- | :--- | :--- |
| 召回 `memcore.recall._scan` | 遍历 `store.iter_items()`，逐条算词法 Jaccard；语义/时间/图通道另算 | **否**；不走 W，候选上限 `candidate_limit=200` 是在全量打分之后才截断 |
| 巩固 `consolidation.replay_cluster` | 每簇自己的局部 W（`MAX_CLUSTER=200`） | **否**；簇 ≤200，全局 50k 的 M=15,000 没有意义 |
| 记忆窗口「以它为线索召回」 | 调 `recall`（探针参数） | **否**；同召回 |
| 热度面板 | 关联图 A 的逐条支撑度 | **否**；不碰 W |
| `axo.bench.substrate` / `tools/bench_consolidation.py` | 全局 W 补全 / 分簇 W | 是，但这是**量具/研究脚本**，不是用户路径 |

也就是说：M=15,000 的 100% 一致 / 70–90 ms 是在**全局 W 补全**这个研究测量上成立的；
Axo 的实际召回不读 W，实际巩固只读 ≤200 条的簇。把它接进 `recall` 会改变召回语义
（召回不是 W 补全），接进 `replay_cluster` 则是在一个 ≤200 条的子集上用一个 15,000
的候选上限——两者都不成立。

## 如果要在 Axo 上做真正的 50k 加速

真正的瓶颈在**召回扫描**，不是全局 W：

1. `_scan` 对 5 万条逐条 `iter_items()` + 词法 Jaccard；`candidate_limit` 在打分之后
   才截断，所以它不影响扫描成本。
2. 语义通道还要对全库嵌入做余弦；时间窗与图通道各有自己的开销。
3. 一个只按词法位建的倒排索引可以加速**纯词法**路径，但生产召回可能同时有语义/
   时间/图通道；候选必须取这些通道的并集，否则会漏掉“无语法重叠但语义命中”的记忆。
   这不是把 M=15,000 接进去，而是一个新的召回候选设计。

因此下一步若要做，应该是：

- 先在**真实 50k 库**上量 `recall` 的扫描耗时与通道占比（当前没有真实 5 万条库）；
- 再决定是“词法倒排 + 语义 ANN + 时间窗 + 图邻居的并集”，还是保持全量扫描；
- 这个设计要按召回四项指标做门槛，不能只按候选一致率。
