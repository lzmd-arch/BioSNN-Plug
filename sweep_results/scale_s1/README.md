# 规模实验 S1：资源与可行性——**稀疏 8192 只吃 767 MiB、约 12 分钟/epoch**（2026-11-03）

> ⚠️ **2026-11-03 更正（见 [S4](../scale_s4/README.md)）**：本页的显存数字**是评测批次造成的**。
> 8192 那 767 MiB 几乎全部来自 `predict(200 个测试样本)`；**训练一次 update 只要 81 MiB**。
> 因此「0.48 MiB/神经元」「8 GB 上限」这类推论**作废**——8 GB 限制的是一次评测多少样本，不是模型大小。
> 本页的**时间**数字不受影响（update 的墙钟是实测的）。

**预注册：** [`research/scale/prereg-s1.md`](../../research/scale/prereg-s1.md) +
[`amend1`](../../research/scale/prereg-s1-amend1.md)（精度对比移到 S2）

## 判决：两条都过

| # | 判据 | 门槛 | 实测 | |
| :--- | :--- | :--- | :--- | :--- |
| **S1-0** | 所有配置在 8 GB 内跑完 | < 8,000 MiB | 稀疏 8192 → **767.1 MiB** | ✅ |

## 稀疏臂（事件驱动，CUDA，600 样本 1 epoch）

| n_rec | 稀疏权重 | 显存峰值 | 一次 update | 60k 样本 1 epoch（外推） |
| ---: | ---: | ---: | ---: | ---: |
| 1,024 | 32,768 | **126.0 MiB** | 0.099 s | 12.4 min |
| 2,048 | 65,536 | 217.6 MiB | 0.096 s | 12.0 min |
| 4,096 | 131,072 | 400.8 MiB | 0.094 s | 11.7 min |
| **8,192** | **262,144** | **767.1 MiB** | **0.094 s** | **11.7 min** |

**"一次 update"几乎不随规模变**——因为 fan-in 固定 32，每个神经元的计算量与 `n_rec` 无关；
变的只有**显存**，而它随规模近线性（126 → 767 MiB，8 倍规模涨 6.1 倍）。

准确率那一列（0.25–0.31）**没有意义**：600 个样本、1 个 epoch。按预注册，不作精度结论。

## 稠密臂（复用已有实测，**预算不同**）

来自 [`sweep_results/phase4_scale/`](../phase4_scale/README.md)（sMNIST，2 epoch，种子 0，β=0）：

| n_rec | 峰值显存 | s/epoch |
| ---: | ---: | ---: |
| 256 | 1,688.6 MiB | 55.6 |
| 512 | 3,116.2 MiB | 133.3 |
| 1,024 | 5,989.7 MiB | 435.3 |
| 2,048 | **11,744.8 MiB** | 2,646.8 |

**2048 已经 11.7 GB，超了 8 GB**——这就是 ADR-0031 里"稠密上限约 1.35k"的来源。

## 这两条曲线放在一起说明什么

| | 8k 神经元要多少显存 | 一个 epoch 多久 |
| :--- | ---: | ---: |
| 稠密 | **放不下**（1k 就要 5,990 MiB） | —— |
| **稀疏** | **767 MiB** | **≈ 12 分钟** |

**5k–8k 在稀疏路径上不是勉强放得下，是只用了一成显存。** 所以 ADR-0031 那个
"放得下之后值不值"的问题，前半已经答了：**放得下，而且很宽裕**；剩下的全是"值不值"。

## 一个顺手修掉的实现缺口

`scripts/run_event_driven_10k.py` 原来**没有 `--device`**，输入留在 CPU——历史那次 10k
（40 分钟 / acc 0.697）是**CPU 跑的**。这次加了 `--device cuda`（同时记录 `peak_mb` 与
`sparse_weights`），才量到上表的数。

这不是"换个设备就快了"的结论：GPU 版 600 样本 7 秒里大部分是数据加载，`s/update` 才是可比量。
