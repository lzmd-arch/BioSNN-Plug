# 预注册：W2 的规模-资源曲线（峰值显存与每 epoch 耗时 vs 循环层规模）

**定稿时间：2026-10-16（中国标准时间），在这条曲线的任何数据之前。**
本文里的既有数字（1,104.1 MiB、3,220.6 MiB）是**动机**，不是依据。

## 它要回答什么

§5.5 现在只能报**一个规模**下的资源数字，而论文里跟显存有关的主张是**跨规模**的：e-prop 的
资格痕迹按突触存储，空间复杂度随神经元数**二次增长**（§2.1，出处为 Pes et al. 2025 的 Table 3
与 §1.3.1）。**一个规模上的一个数字支撑不了二次增长这句话。**

所以补这条曲线，并明确它要产出**两个**量：

1. **峰值显存 vs `n_rec`**（log-log）——它直接对上"二次增长"那个主张；
2. **每 epoch 耗时 vs `n_rec`**（log-log）——消费者级部署的可行性依据。

顺带回答一个**实现层**的问题：`docs/adr/ADR-0010` 记着 LIF（β=0）下"整个迹的状态可降到
O(batch·N)"——**那句话写进了代码注释、没有验过**。若实测在 LIF 上仍露二次项，说明这条管线的
LIF 路径并没有走那个可降维的形式。**这是一个可能出现的负面发现，先说好：出现了照实写。**

## 设计与判据（先写死）

| 维度 | 取值 | 为什么 |
| :--- | :--- | :--- |
| `n_rec` | **64 / 128 / 256 / 512 / 1024 / 2048** | log2 等距，`n_rec=256` 那档与官方臂重合、可交叉核对 |
| 预算 | **2 epoch × 种子 0** | 资源由规模与形状决定，不由 epoch 数决定；2 epoch 足够让分配器到达稳态 |
| 其余 | sMNIST、batch 64、lr 1e-2、**beta=0（LIF）** | 与官方收官臂同一个神经元模型——曲线要描述论文真在跑的管线 |
| 记录口径 | `peak_mb` 用 **PyTorch 分配器**（`max_memory_allocated`），不是 `nvidia-smi` | 后者含其它进程与缓存，会把结果抬高到无法归因（与 W3 同口径） |

**报告的判据**：

* 两个量都用 **log-log 最小二乘斜率** 报；斜率 1.0 = 线性、2.0 = 二次。
* 斜率**是结果不是前提**：若不落在 2 附近，照实报，并说明二次项可能被别的分配盖住了。
* 表里同时给**原始点**（不拟合外推、不给"估计值"）。

## 边界情况（先说好）

* ⚠️ **大端可能 OOM**（8 GiB 卡，2048 那档）。失败**如实记为该档失败**，拟合只用完成的点，
  并在论文里写明"最大只测到 X"。**不得**用估计值补上失败的点。
* ⚠️ **本机同时在跑别的 GPU 作业时不许跑**：显存峰值不受负载影响，**耗时受**（本仓实测过
  1.5× 的差）。若跑的时候机器不干净，耗时那半张图作废、显存那半张仍可用——这一点要写进结论。
* 这条曲线与 §5.2 的任何准确率数字**不可比**：2 epoch、单种子下的准确率没有意义，
  日志里会打印它，但那只是诊断。

## 这份预注册**不**声称什么

* 不声称"e-prop 在消费者硬件上能训到多大规模"——只测到 2048，且只是单层循环。
* 不声称这条曲线的斜率适用于别的实现：它描述的是**这一份实现**在**这台机器**上的分配行为。
* 不给外推。50k 神经元那句是另一个问题，需要另一种办法（外推是计划书 §6.2 的显存约束声明要做
  的事，与本条分开）。
