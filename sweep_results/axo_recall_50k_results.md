# 真实 50k 召回 profiling 与 MMR 优化

**日期：2026-10-18。** 数据是 `benchmarks/substrate` 的真实文本按
`scaled_memories` 放大到 50,000 条；用真正的 `MemoryStore` + `recall`，不是 SDR
层面的模拟。

## 一句话

**MMR 是召回的真热点，不是扫描。** 把逐对 `SDR.jaccard` 换成候选 0/1 矩阵后，
5,000 条单次召回 **4.19 s → 1.22 s**，金标准四项逐位不变；50,000 条从约 15 s
量级降到 **9.09 s**，剩下的瓶颈是 `_scan`（`iter_items` + 词法 Jaccard），不是 MMR。

## 5,000 条（同一库，同一查询）

| 版本 | 单次召回 |
| :--- | ---: |
| 逐对 Jaccard（旧） | 4.19 s |
| 候选矩阵（新） | **1.22 s** |

cProfile（旧版）显示 9.28 s 里 `_best_mmr` / `_max_jaccard` 占 7.7 s，其中
`np.intersect1d` 占 3.8 s、`ndarray.sort` 占 1.8 s；`_scan` 只占 1.5 s。

## 50,000 条（新 MMR 版）

| 阶段 | 耗时 |
| :--- | ---: |
| 编码 50k 词法 SDR | 80.16 s |
| 建库（50k 次 add） | 3.03 s |
| `iter_items`（解码 50k SDR） | 3.87 s |
| **一次词法召回** | **9.09 s** |
| 建倒排索引 | 13.15 s |
| 倒排 gather + Jaccard（5 查询均值） | 2.15 s（候选 50,000） |

- 50k 上倒排候选**没有缩小集合**：这份放大语料同簇拼接，几乎所有条目都共享
  公共位，候选数就是全库 50k。所以“纯词法倒排”在这份语料上不成立；真实库需要
  用稀有位的 IDF/图邻居才能缩小。
- 剩余 9 s 主要是 `_scan`：50k 次 `iter_items` 解码 + 词法 Jaccard + token 估算；
  MMR 不再是主项。
- 没有真实 5 万条记忆库；这份是同簇拼接的放大语料，数字不能直接读成真实库。

## 已落地的 Axo 改动

- `src/memcore/recall.py`：`_select` 用 `_jaccard_matrix` 预计算候选两两 Jaccard，
  `max_sim` 向量维护 MMR 的冗余度；删除了逐对的 `_best_mmr` / `_max_jaccard`。
- 语义与原实现一致：`SDR.jaccard` 刻意忽略权重，所以 0/1 矩阵同义；宽度不一致
  的候选按 0 相似度处理。
- 金标准词法四项逐位不变：hit@1 0.8961 / hit@8 0.9481 / MRR 0.9095 /
  误注入 0.8679 / AUC 0.9289。
- 已推送 Axo `main` `357e757`；相关测试与 pre-commit 全过。

## 下一步（真 50k 的剩余瓶颈）

1. **稀有位候选**：按每位 `df` 排序，先用稀有位的倒排表 gather，再补公共位；
   在 50k 放大语料上测候选缩小与 top-1 一致率。
2. **避免全量 `iter_items`**：候选确定后按 id 取条目，而不是解码全库 SDR。
3. **token 估算惰性化**：只对进入候选池的条目算，或缓存。
4. 语义/时间/图通道的候选并集：生产召回不能只按词法位过滤，否则会漏语义命中。

MMR 优化后 50k 单次召回 1.96 s（warm；索引首次构建 22.3 s），仍然不是终态。

## 词法倒排候选落地（Axo `bc59387`）

- `MemoryStore.lexical_index()`：按 `lex_*` 列建 CSR 倒排，按 `revision` 失效；
  `get_many()` 批量取候选条目。
- 纯词法路径（无语义 query_vector、`graph_weight<=0`、无时间窗、全部条目有词法码）
  使用候选；其他情况全量扫描。
- 50k 实测：索引首次构建 **22.3 s**；之后一次召回 **均值 1.96 s、中位 1.83 s**
  （之前 9.09 s）。5k 上候选路径 1.66 s，比矩阵版 1.22 s 略慢——候选数等于全库，
  没有收益。
- 金标准词法四项逐位不变；`tests/test_lexindex.py` 覆盖倒排、缓存失效与 `get_many`。
- 50k 的 1.96 s 仍不是终态：剩余是 5,000 条候选的 get_many + 扫描 + MMR；语义/
  时间/图通道仍走全量。下一步是并集候选，并把索引构建移出召回热路径。

## 多通道并集与嵌入缓存（Axo `7074f6e`）

给 50k 条记忆加**确定性合成 768 维向量**（只量通道耗时，不量语义质量）：

| 场景 | 候选 | warm 召回 | 首次召回 |
| :--- | ---: | ---: | ---: |
| 纯词法倒排 | 5,000 | 1.96 s | 1.33 s + 索引 22.3 s |
| 词法 + 语义并集（缓存前） | 9,497 | 7.01 s | 7.83 s |
| 词法 + 语义并集 + 归一化矩阵缓存 | 9,497 | **5.22 s** | 7.62 s |

- `_prefilter_ids` 取词法倒排 + 语义 top-M + 时间窗 + 图正分的并集；并集 >20,000
  或存在无词法码条目时退回全量扫描。
- `normalized_embedding_matrix` 按 embedding revision 缓存，省掉每轮 153 MB 的
  复制与归一化；语义 warm 7.01 s → 5.22 s。
- 金标准词法四项仍逐位不变。
- 语义 5.22 s 仍远高于纯词法：9,497 条候选的 `get_many` + 扫描 + MMR，加上
  50k×768 的余弦与候选排序。**已按"降低并集上限 + 精确候选排序"处理（见下节），
  不引入 ANN**（LSH 在真实 166 上 top-50/top-100 召回只有 0.94/0.91，见
  `axo_semantic_ann_results.md`）。

## 候选排序修正：按精确 Jaccard 取前 1,000（2026-10-19）

**旧实现选错了候选。** `LexicalIndex.candidates` 原先按位的文档频率从稀有到常见
gather，凑满 `_PREFILTER_LIMIT` 就停。5 万条放大语料、40 条 substrate 查询上：

| 上限 | top-8 覆盖率（旧） | 旧 hit@1 | 旧 hit@8 | 精确 Jaccard hit@1 | hit@8 | MRR | 精确排序耗时 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.287 | 0.000 | 0.050 | **0.850** | **0.975** | 0.892 | 161 ms |
| 2,000 | 0.341 | 0.000 | 0.075 | 0.850 | 0.975 | 0.892 | 167 ms |
| 5,000 | 0.475 | 0.000 | 0.100 | 0.850 | 0.975 | 0.892 | 152 ms |
| 10,000 | 0.678 | 0.000 | 0.075 | 0.850 | 0.975 | 0.892 | 160 ms |

差别不在上限大小，而在**谁被留下**：一条与查询共享 3 个公共位的记忆，Jaccard
可能高于只共享 1 个稀有位的记忆，而出现顺序会先撞上后者。精确排序用与
`SDR.jaccard` 相同的集合口径（忽略权重），因此候选阶段不改变最终融合语义。

**端到端**（真正的 `recall`，预算无限、默认 `candidate_limit=200`）：

| `_PREFILTER_LIMIT` | hit@1 | hit@8 | MRR | 单次召回 |
| ---: | ---: | ---: | ---: | ---: |
| 500 | 0.8500 | 0.9750 | 0.8917 | 774 ms |
| 1,000 | 0.8500 | 0.9750 | 0.8917 | 847 ms |
| 2,000 | 0.8500 | 0.9750 | 0.8917 | 1,270 ms |
| 5,000 | 0.8500 | 0.9750 | 0.8917 | 1,991 ms |
| 全量 50,000 | 0.8500 | 0.9750 | 0.8917 | 8,779 ms |

四项指标在所有上限上逐位相同；耗时随候选数线性增长。取 **1,000**，给融合后的
`candidate_limit=200` 留 5 倍余量。机器当时有其它重活在跑，绝对毫秒只读相对值。

**索引构建移出热路径。** 新增 `axo.ui.memory_worker.LexicalIndexWorker`：库 ≥
2,000 条时，主窗口启动后台预建词法索引。构建仍要 22.3 s（50k），但不再发生在
用户说完第一句话、等回复的那条调用栈里；失败时首轮召回照常重试。

金标准 `tools/bench_recall.py --no-semantic --check` 仍逐位不变：
hit@1 0.8961 / hit@8 0.9481 / MRR 0.9095 / AUC 0.9289。

### 语义并集复测（上限 1,000）

同一份 50k 语料、确定性合成 768 维向量（只量通道成本，不量语义质量）：

| 版本 | 候选 | warm 召回 | 首次召回 |
| :--- | ---: | ---: | ---: |
| 并集 + 上限 5,000（`7074f6e`） | 9,497 | 5.22 s | 7.62 s |
| 并集 + 精确排序 + 上限 1,000 | **1,979** | **2.59 s** | 4.88 s |

候选降到约五分之一，warm 召回降到约一半。剩余成本主要是 50k 条语义余弦、
`_contrast` 与 2k 条候选的扫描；机器当时有其它重活在跑，绝对毫秒只读相对值。

## 增量词法索引：新增不再整库重建（2026-10-19）

**问题**：`MemoryStore.add` 每次让 `_revision + 1`，下一次 `lexical_index()` 整库
重建。50k 上静默机器实测 **3.8–5.0 s**（有重活并行时 22 s）；真实库每轮对话都可能
新增一条记忆，等于每轮都付一次。

**改法**：`LexicalIndex` 保留 base CSR，另加一小段 delta CSR。新增一条只把它的
573 个位并进 delta（不碰 base）；`candidates()` 把 base 与 delta 的 posting 一起
`bincount`。delta 满 512 条后下一次 `lexical_index()` 做一次全量合并。覆盖既有 id
的 UPSERT 与删除仍让索引失效并整库重建——它们是低频动作，不值得维护 tombstone。

| 操作 | 实测 |
| :--- | ---: |
| 50k 首次建索引 | 3.52 s |
| 前 100 条新增（已建索引） | **1.50 ms/条** |
| 再 412 条（delta 接近上限） | 9.27 ms/条 |
| delta 满 512 后的全量合并 | 3.53 s |
| 新增期间召回（1,000 候选） | 91 ms |

按 512 条摊，全量合并约 7 ms/条；加上 delta 的维护，新增一条的索引成本从
**3.5–5.0 s 降到约 10 ms 量级**。候选与全量重建的一致性用 200 条小库 + 50 条新增、
6 条查询逐集合核对过。

同批的纯 Python 热路径优化：`is_cjk` 从生成器 `any(...)` 改成有序区段提前返回
（2,000 条语料 47 ms → 16 ms）；`estimate_tokens` 对 ≤4,096 字的正文按内容缓存，
避免每轮把同一批候选重新逐字符扫一遍。

## 图通道：种子走索引，正分截到 5,000（2026-10-19）

**旧实现为图节点的种子分 `iter_items()` 解码全库 SDR**，50k 上实测 2.3–3.1 s；
而候选路径已经有同一套位索引。改用 `LexicalIndex.scores()` 后：

| 项目 | 旧 | 新 |
| :--- | ---: | ---: |
| 种子计算（50k） | 2.30–3.09 s | **0.079 s** |
| `_graph_channel` 总计 | — | 0.079 s |
| 正分节点 | 50,000 | 50,000 |
| 候选并集 | >20,000 → 全量扫描 | **5,251** |
| 端到端召回（1,000 词法 + 图） | 约 9 s + 种子 | **552 ms** |
| 扫描条数 | 50,000 | 5,251 |

- 50k 放大语料上查询与几乎全库都有词面碰撞，种子与扩散正分都是 50,000 条；
  `_prefilter_ids` 的 20,000 上限必然触发。新增 `_GRAPH_CANDIDATE_LIMIT = 5000`，
  只把扩散分最高的 5,000 条并进候选，不改变被扫条目的打分。
- `scores()` 保留"宽度不同不给种子"的守卫；新增单测逐条对比 `SDR.jaccard`。
- 图用**链式 stub**（每个节点一条出边）：只量通道成本与正分规模，不是真 50k 图。
  真 50k 图建图本身要 259 s，没有在这一轮做。

## 时间窗：召回只取 id（2026-10-22）

时间窗候选子集只需要 id，随后 `_scan` 会按 id 批量取条目。旧路径
`items_created_between` 先把窗内每条记忆的正文与 SDR 解码一遍，等于白解一次。
新增 `ids_created_between` 只 `SELECT memory_id`：

| 50k 覆盖全库的宽窗口 | 实测 |
| :--- | ---: |
| 整行版本 `items_created_between` | 1.18 s |
| 只取 id `ids_created_between` | **0.045 s** |
| 加速 | 26× |

语义不变（半开区间、不按 tier/taint/pinned 过滤、同序）；整行版本留给主动搭话等
确实需要正文的调用方。召回金标准四项逐位不变。
