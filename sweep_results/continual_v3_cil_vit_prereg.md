# 预注册：用 ViT-B/16 特征重跑 CIL，量"离 0.8 还剩多少"（2026-11-04）

**状态：判据先落盘。** 这是 ADR-0029 重开条件里那个 **0.8** 的直接测量。

## 为什么要跑这一轮

ADR-0029 写的是"任务推断能到 **0.8** 以上"，同一行把 0.5855 / 0.1285 记成 ACC / AF 一对，
**所以按字面，0.8 指的是端到端 ACC**。而 0.5855 是在 **ResNet18** 特征下测的。

今天量出来的事实（[`continual_v3_backbone_ceiling`](continual_v3_backbone_ceiling/README.md)）：
ViT-B/16 的**任务路由**上限是 **0.7912**，远高于 ResNet18 的 0.6512；它的细类准确率是 0.809 对 0.663。

**但路由上限不等于端到端 ACC。** 端到端还取决于每任务头的质量、以及路由与头的配合。
这一轮把那个数直接跑出来。

## 设计（跑之前定死）

同一套 CIL 协议（CIFAR-100、10×10、按类 id 升序、delta 线性读出、不提供任务 id），
只把特征从 ResNet18 换成 **ViT-B/16（768 维）**，两个臂：

| 臂 | 命令里的任务推断 | 说明 |
| :--- | :--- | :--- |
| **O（上界）** | `--task-inference oracle` | 给真实任务 id，量"特征更好之后天花板在哪" |
| **R（可部署）** | `--task-inference mahalanobis-full` | 全协方差路由，与 ResNet18 那一轮同一个做法 |

单种子（0），其余参数与 `task_inference_mahalanobis_full` 那一轮**完全一致**
（hidden 1 epoch、读出 eta 0.01 × 20 epoch、batch 128）。

## 判据

| # | 判据 | 门槛 |
| :--- | :--- | :--- |
| **G-0** | 前置：特征确实更强 | `ACC_O ≥ 0.85`（ResNet18 的 oracle 是 0.8195） |
| **G-1** | 达到 ADR-0029 的字面门槛 | `ACC_R ≥ 0.80` 且 `AF < 0.08` |
| **G-2** | 有实质进步 | `ACC_R ≥ 0.70` |
| **G-3** | 不只是头变好 | `ACC_R − ACC_O ≥ −0.20`（路由没把上界优势吃光） |

**G-1 过 → 纯 CIL 的重开条件之一就满足了**（另一条"真实长序列"仍然缺）。
**G-1 不过而 G-2 过 → 方向对、还不够**，要写清差多少。
**G-2 也不过 → 说明路由那 0.79 的上限没转化成端到端收益**，那要回头查组合方式。

## 预期

**押 G-0 过、G-1 不过、G-2 过。** 具体：`ACC_O` 落在 0.88–0.90，`ACC_R` 落在 **0.70–0.75**。

理由：ResNet18 下 oracle 0.8195 → 路由 0.5855，路由把上界吃掉了 28%。ViT 的路由率更高（0.7912），
掉得会少，但每任务头在 768 维上的行为没测过，不敢押太满。

## 边界

- **单种子**；只跑两个臂，不扫超参；
- 换骨干**会改变基准的含义**（`frontends.py` 明写这条）——本轮的数字**不能**与 ResNet18 那轮的
  0.5855 / 0.8195 直接并列成"同一基准下的提升"，只能作为**换特征空间之后的新读数**；
- ViT 特征已缓存（`data/_features/vit_b_16_*.npz`），不再重算；
- 不因为 G-2 不过就换路由方法重跑。

## 成本

特征已缓存；delta 读出是 numpy，CPU 上每臂约 10–20 分钟，两臂 **约 40 分钟**。
