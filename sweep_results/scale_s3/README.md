# 规模实验 S3：16k 贴着 8 GB 上限，边际收益已经掉到 1pp 一档（2026-11-03）

> ⚠️ **2026-11-03 更正（见 [S4](../scale_s4/README.md)）**：标题里的「贴着 8 GB 上限」**是错的**。
> 7,489.5 MiB 里有 **7,309.0 MiB 来自 `predict(1000 个测试样本)`**；**训练一次 update 只要 129.9 MiB**。
> 所以「16,384 是 8 GB 上的终点、硬上限约 17.5k」**作废**。
> **准确率与时间的那三条不受影响**：0.774 / 0.788 / 0.797 与 ~1,100 s 都是实测的。

**预注册：** [`research/scale/prereg-s3.md`](../../research/scale/prereg-s3.md)

## 判决：三条都过，但两条是踩线

| # | 判据 | 门槛 | 实测 | |
| :--- | :--- | :--- | :--- | :--- |
| **S3-0** | 两个规模都放得下 | < 8,000 MiB | **7,489.5 MiB**（16,384） | ✅ 只剩 **511 MiB** 余量 |
| **S3-1** | 继续爬坡 | `acc(16384) − acc(8192) > 2pp` | **+2.3pp** | ✅ 超出门槛 **0.3pp** |
| **S3-2** | 时间没爆 | ≤ 1.5 × 1,101 s | 1,071 s | ✅ |

## 三个点

| n_rec | 准确率 | 相对上一点 | 显存 | 耗时 |
| ---: | ---: | ---: | ---: | ---: |
| 8,192 | 0.774 | — | 3,899.5 MiB | 1,101 s |
| 12,288 | 0.788 | **+1.4pp**（×1.5 规模） | 5,671.2 MiB | 1,083 s |
| **16,384** | **0.797** | **+0.9pp**（×1.33 规模） | **7,489.5 MiB** | 1,071 s |

## 这一轮真正的读数：斜率塌了

| 区间 | 每翻一倍涨多少 |
| :--- | ---: |
| 1024 → 2048 → 4096 → 8192（S2） | **≈ +5pp / 倍** |
| 8192 → 12,288 | **+1.4pp**（×1.5） |
| 12,288 → 16,384 | **+0.9pp**（×1.33） |

**S3-1 虽然过了，但它是踩线过的（2.3 vs 2.0）。** 按每档 1pp 的斜率，**再往上已经换不来什么**，
而 8 GB 也快没了：16,384 已经吃掉 **93.6%** 的显存预算。

按实测 **0.457 MiB/神经元** 外推，8 GB 的硬上限约 **17.5k**——**16,384 基本就是这条路径的终点**。

## 对主线的意义

ADR-0031 写了两条相关的东西：

- 回退条件「5k–8k 相对 1k–2k 提升 ≤2pp」——**没有触发**（S2 就 +14.6pp）；
- 但**加宽这条轴已经走到物理尽头**：再往上放不下，而最后 2 倍规模只买到 2.3pp。

所以主线不该继续"加宽"，而该**换轴**。候选（都要先写预注册）：

| 轴 | 说明 |
| :--- | :--- |
| **fan-in** | 现在固定 32。稀疏权重只有 524k，显存的大头不是权重——加大 fan-in 可能比加神经元更划算 |
| **batch / 训练轮数** | 2 epoch 下容量是决定性的；训练更久会不会把差距抹平，S2 的边界里留了这个口子 |
| **任务** | sMNIST 在 250 epoch 下 256 神经元就到 0.8889；换一个更吃容量的任务，规模曲线可能是另一条 |

**倾向先做 fan-in**：它是唯一"不额外吃神经元显存、直接加计算连接"的轴，而现在的显存瓶颈
恰恰不在权重上（524k 权重只有 2 MB，7.5 GB 花在别处）。这一条要先弄清楚"显存到底花在哪"。

## 边界

- 2 epoch、单种子；16,384 只测了一次，±1pp 的差异分不清；
- 16,384 的 7,489.5 MiB 是 PyTorch 分配器口径，不含驱动/上下文开销——真实占用更高，8 GB 卡已经不能同时跑别的；
- 不与 W2 的 250-epoch 0.8889 比较。
