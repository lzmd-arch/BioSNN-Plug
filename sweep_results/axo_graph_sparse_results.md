# 关联图建图加速原型：稀疏 posting vs 稠密 BLAS

**日期：2026-10-26。** 关联码每条只有 64 个活跃位，而 `GraphIndex.build` 用 4096
宽的稠密指示矩阵做分块乘法。这里用同一份关联码、同一个 `top_m=8` /
`min_weight=0.1`，改成按位 posting 取交集再选 top-m，比较边与耗时。

## 结果

| n | 稠密 `GraphIndex.build` | 提取关联码 | 稀疏 posting | 稀疏总计 | 稠密/稀疏 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2,000 | 1.17 s | 0.91 s | 0.29 s | 1.21 s | 0.97× |
| 20,000 | **46.0 s** | 9.81 s | 45.31 s | 55.1 s | 0.84× |

- 两档的**边权最大差都是 0.0**；但邻接索引大量不同——放大语料里同簇拼接产生大量
  同分近重复，稠密侧 `argpartition` 与稀疏侧稳定排序在并列时选了不同节点。这是
  语料的并列，不是分数算错。
- 稀疏版没有更快：逐节点 `bincount` + `lexsort` 的 Python 循环，把少算的乘法又
  吃回去了。稠密分块乘法走 BLAS，20k 上已经很有效。

## 结论

**不把稀疏 posting 换进生产。** 建图 193.6 s（50k）仍然是长任务，但“少算 4096 宽
的零”不是可行的加速方向；剩下的现实选项是：

1. 接受全量重建，只把“新记忆不在图里”说清楚（已落地）；
2. 设计真正的增量图（需要处理新节点进入既有节点 top-m 的对称更新），或者；
3. 产品上决定一个“缺失多少条之后后台重建”的策略。
