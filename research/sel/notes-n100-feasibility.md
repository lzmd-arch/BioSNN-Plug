# N100 可行性三条验证（2026-11-12 凌晨）

三条都是**部署前的前置**，用现有小模型做的，不需要训 1B。

## H-A：树读出按行 int8 量化（推理期）—— **通过**

KdConv、V=3,001、4,000 步、K=2、树、`signal_scale=3`。

| | top-1 | top-5 | top-10 | CE | 期望选择成本 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| fp32 | 0.2820 | 0.4954 | 0.5860 | 4.0284 | 6.1759 |
| **int8（按行）** | 0.2816 | 0.4948 | 0.5856 | 4.0318 | 6.1816 |
| **Δ** | **−0.04pp** | −0.06pp | **−0.04pp** | +0.003 | +0.006 |

判据是 top-10 掉 ≤1pp，实测 **−0.04pp**，余量 25 倍。

**意义**：N100 上每 token 的权重读从 **1.02 MB 降到 255 KB**。推理期量化是**一次性损失**
（权重只读），与训练期"权重即累加器"完全是两回事——后者实测 −11pp，不能混为一谈。

**限定**：按行 scale。整表一个 scale 会让小幅值的行整行归零。

## H-B：`emb·proj` 折叠成稠密 `w_in` —— **通过（逐位相同）**

```
emb[t] @ proj  vs  (emb @ proj)[t]   ⇒  max|Δ| = 0.000e+00
折叠矩阵 32,000×10,417 = 333M 参数 = 1.33 GB fp32 / 0.33 GB int8
推理每 token gather 一行 = 42 KB
```

**意义**：训练用低秩（省 FLOP），**导出时折叠成稠密**（推理省访存）。
低秩在 CPU 推理上是灾难——每 token 要读整张 `proj`（15.8 MB），比树读出大 15 倍。

## H-C：三个头的代价 —— **数字部分是坏消息**

`s ≡ 0` 时特征逐位相同（S-0 守卫成立），但代价表暴露一个必须改的设计（M=20,834）：

| 头 | 参数 | 每 token 读 | 相对树读出（1.02 MB） |
| :--- | ---: | ---: | ---: |
| 风格 `s`（S=8） | 0.17M | 0.67 MB | **66%** |
| 触发器（M×2） | 0.04M | 0.17 MB | 17% |
| **记忆编码（M×256）** | 5.33M | **21.33 MB** | **21 倍** |

**记忆编码按原设计在 CPU 上不可行**：每 token 读 21 MB，把 N100 从 28k tok/s 压到 1.3k。
三条修法（已写进 SEL 预注册的限定）：

1. 只在**写记忆时**算一次，不是每 token；
2. 降到 d=32（成本 2.7 MB）；
3. 复用树的稀疏访问模式。

风格头 66% 也要处理：S 降到 2–3，或只加在部分特征上。

**干扰为零是构造保证**：触发器与记忆编码是**只读消费者**，不回写基底；风格头只在 `s≠0` 时改变 logits。
真正的风险不是干扰，是**特征里有没有这些信息**（M-3 的前车之鉴）。
