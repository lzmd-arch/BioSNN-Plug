# 预注册修正 4：**实测**推翻 amend2/amend3 的成本模型（2026-11-11）

**amend2/amend3 的 `V/(B·depth)` 不是普适的成本比，只是"稠密路径已经访存受限"时的下界。**
实测把这个前提推翻了。以下是实测，工具是 `research/sel/lm/bench_hierarchical.py`（已入库）。

## 一、代价模型错在哪

`V/(B·depth)` 只比较了"两边读多少行"。但稠密读出 `features @ W` 的算术强度是
**B MAC / 元素**（B=256 时 128 FLOP/byte），它在我们所有工作点上都**算力受限**，
不是访存受限。树路径的算术强度只有 **1 MAC / 元素**，是访存受限的。

所以正确的比值是两者各自受限时的比值，而**不是**行数比。`V/(B·depth)` 只在
稠密也变成访存受限（B 足够大）时才成立——实测到 B=4,096 **都还没有**。

## 二、实测：同一形状下"整步"（前向 + 信号 + 更新）的倍数

| 形状 | 稠密 | **树** | 倍数 |
| :--- | ---: | ---: | ---: |
| V=3,001 M=2,048 B=256（KdConv） | 1.35 ms | 2.38 ms | **0.57x（树更慢）** |
| V=32,000 M=4,096 B=256 | 21.2 ms | 3.22 ms | **6.58x** |
| V=32,000 M=4,096 B=64 / 1,024 / 4,096 | — | — | 10.90x / 6.23x / 7.83x |
| V=32,000 M=16,384 B=256（1B） | 97.9 ms | 336.8 ms | **0.29x** ⚠️ 见下 |

**⚠️ 最后一行的 0.29x 不可信、也不许引用。** 那张卡当时只剩约 5.9 GB 空闲，
而这张表要放两个 2.1 GB 的矩阵（稠密 `(M,V)` + 树 `(N−1,M)`）外加每步约 300 MB 的临时张量，
余量不足、allocator 在反复换页。**必须在独占 GPU 的窗口重测，重测之前 H-2 不判。**

## 三、被实测推翻的两条

1. **"批量越大树越不值"**（amend2 第三节）——**不成立**。
   V=32,000 / M=4,096 下 B=64→4,096 的倍数是 10.90 / 6.23 / 7.83，
   **基本平坦**，因为稠密侧一直算力受限、每 token 成本不随 B 下降。
   amend2 那张"B=2,048 ⇒ 1.87x"的表作废。
2. **"KdConv 上树快 1.41x"**（amend3）——**不成立**，实测 **0.57x（更慢）**。
   小词表上树的固定开销（多出来的内核数与 gather 延迟）压过了省下的行数。

## 四、一条实现事实（已改进代码）

**逐层 `for j in range(depth)` 写是会毁掉收益的**：V=3,001 上逐层是 **0.22x**，
摊平成一次 `index_select` / 一次 `index_add_` 之后是 **0.92x**（同形状）。
`TreeReadout.step` 已经改成扁平实现，峰值临时是 `(B·depth, M)`
（1B 形状约 177 MB）。

## 五、这一步之后判据怎么走

| 判据 | 状态 |
| :--- | :--- |
| **H-1（质量）** | 照跑（KdConv、16,000 步、2 抽头、V=3,001），**只判质量**。该形状下树更慢，与质量无关 |
