# 立项：Rust 稀疏 SNN 核 —— 重判"稀疏到底行不行"（2026-11-11）

**性质：立项 / 预注册，尚未开工。** 判据先落盘。

## 先把反方观点放在最前面（这一条决定它值不值得做）

> **Rust 只解决"快"，不解决"准"。**

我们砍掉的稀疏方案，**死因有两种，必须分开**：

| 方案 | 死因 | Rust 能救吗 |
| :--- | :--- | :--- |
| A1 候选剪枝 | **慢 25×**（`gather` 访存受限） | ✅ 能 |
| 事件驱动读出 | **慢 9–25×**（`nonzero()` 同步 + gather） | ✅ 能 |
| K1 Triton 融合内核 | 端到端 <2%（逐元素链只占一步 2.6%） | ❌ 不能（不是内核问题） |
| **低秩读出 r=512** | **质量 −1.3pp** | ❌ **不能** |
| **候选剪枝的偏置** | **长尾字永远进不了候选**（有偏） | ❌ **不能** |

**⇒ 五条里只有两条是"被 PyTorch 冤枉的"。** 本项目只救那两条，**并且必须同时带质量判据**。

## 要回答的唯一问题

> **在原生实现下，"只算发放的那一部分"能不能把每 token 的成本降下来 —— 且质量不掉？**

现在的答案两边都缺：PyTorch 下必然更慢（它要先物化稠密张量再剪），而"快"从未被公平测过。

## 最小可测接口（MVP，先只做前向）

**不做训练、不做 GPU、不做 1B 主线。** 只做三件事：

1. Rust 实现 **LIF 前向**（膜电位 / 脉冲 / 不应期，与 `research/eprop/neurons.py` 同口径）；
2. Rust 实现**稀疏读出前向**：只在发放的神经元上算 `W[active]`；
3. 与 **PyTorch 稠密参考**逐位对照 + 微基准。

## 判据（先落盘，出数前不得改）

| # | 门槛 | 判什么 | 不过怎么办 |
| :--- | :--- | :--- | :--- |
| **R-0** | 与 PyTorch 参考的前向差 **≤ 1e-5**（同权重、同输入） | 是同一个模型，不是"另一个东西" | 修实现 |
| **R-1** | **稠密 vs 稀疏（密度 1%–4%）**：单核 CPU 上前向 **≥ 5×** | 稀疏的算力优势真的存在 | **判负，整个立项关闭**；此后不再提"稀疏更快" |
| **R-2** | 把 R-1 带回**端到端每 token 成本**：降 **≥ 2×** | 省的不是边角，是主项 | 若 R-1 过而 R-2 不过 ⇒ **瓶颈不在前向**，据实写进结论，不继续投入 |
| **R-3** | 稀疏读出的 **top-1 掉 ≤ 1pp**（同语料、同预算、同种子） | **质量不掉** | 掉了就只保留"推理加速"的叙事，不碰训练 |

**R-1 是判决点，R-3 是准入门槛。** 两条都过才谈集成。

## 2026-11-11 补：**cuSPARSE 推翻了我原先的框架**

立项原文说"稀疏在 PyTorch 里必然更慢，因为要先物化稠密张量再剪枝"。**这句只对
`gather` / `nonzero` 那两条手写路径成立**——它们是 A1 与事件驱动读出失败的原因。
**cuSPARSE（真正的稀疏 GEMM）是第三条路，此前从未测过。**

实测（fp32，B=256、M=16384、V=3001）：

| 密度 | 稀疏 (ms) | vs 稠密 fp32 | vs 稠密 bf16 |
| ---: | ---: | ---: | ---: |
| **1%** | 0.419 | **6.61x** | **4.69x** |
| 2% | 0.731 | 3.79x | 2.69x |
| **4%（本模型实测发放率 4.2%）** | 1.513 | 1.83x | **1.30x** |
| 10% | 4.104 | 0.67x | 0.48x |

**结论：密度是唯一变量。** 我们的工作点（4.2%）只落在 1.30x；**1% 才有 4.69x**。
（bf16 的 SpMM 在本栈上不受支持，只能用 fp32——这本身让稀疏的对手更弱。）

### 新增判据 R-1b（判决点，取代 Rust 在训练侧的定位）

**上面那张表把 CSR 构造放在计时之外，而真实训练里 features 每步都变、每步都要重建 CSR。**

| # | 门槛 | 判什么 |
| :--- | :--- | :--- |
| **R-1b** | **含 CSR 构造**的端到端每 token 成本，在 **4.2% 密度**下相对稠密 bf16 **>= 1.2x** | 稀疏值不值得进训练栈 |
| R-1c | 若能稳定把密度压到 **1%**，同一口径下 **>= 2x** | 压低密度是不是第二条路 |

**R-1b 不过 ⇒ 稀疏只保留"端上推理"的定位，不进训练。**

### 立项定位的修正

- **训练侧**：改由 **R-1b** 判，不再由 Rust 判（GPU 上的 cuSPARSE 才是对手，Rust/SIMD 只在 CPU 上有意义）；
- **端上侧**：Rust 的 25x（4%）/ 306x（1%）仍然成立，仍是 Axo 的一条真路径。

## 为什么值得花这 3–5 天

两条已知被冤枉的方案 + 一个尚未被公平检验的主张：

1. **A1 候选剪枝**：算法上是我们**唯一**能把读出从 `M·V` 降下来的路（低秩那条已因质量判负）。它现在是"快不了"而不是"不好"。
2. **事件驱动读出**：BioSNN 的核心叙事就是事件驱动。**如果在我们自己的硬件栈上稀疏不快，那个叙事就是空的。**
3. **1B × 2 天的结论会重算**：现在按稠密 `M·V` 算需求 16.8 TFLOPS。若稀疏前向真能省 90%，这个门槛显著下降。

## 与主线的隔离

- **不碰** 正在跑的 LM 实验队列（S15 / STREAM-3 / D2 / 建库 / 1B 吞吐探针）；
- **不改** 任何学习规则（e-prop / NLMS 一条不动）；
- **不写** GPU 核（`triton-windows` 那条已判死）；
- 一个 token 的训练成本若没降下来，**不拿它去碰 1B 训练**。

## 边界（写死）

- 单核 CPU 微基准**不等于**整机收益，R-2 必须回到端到端；
- 稀疏收益**依赖发放密度**：今晚测得 4.2%，若训练后密度升高，收益按比例缩水；
- **"快"不等于"能训"**：候选剪枝的偏置问题 Rust 解决不了，R-3 只能守"质量不掉"，守不了"质量变好"。
