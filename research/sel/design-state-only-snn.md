# 快半只做状态：不参与任何词表运算（设计与审查）

## 一、为什么要这样改

四个融合算子（线性、秩、一致性门、可学门）全部卡在同一条线：**它们都活在
token 步进 → 加性嵌入 → 树读出 → 词表分布** 这个接口里。那是 transformer 的接口。
在那个接口里，快半贡献的一切都能被一个温度解释。

⇒ 要让它做它擅长的事，**必须让它的输出不经过词表**。

## 二、什么是"只做状态"

快半每次只输出一个向量 `s_t`（读出特征，或更晚：群体编码/首脉冲时间），
**不产生任何 token、不参与任何 logits、不算 perplexity、不做束搜索**。

`s_t` 的消费者只能是这些（都不是词表）：

| 用途 | 怎么用 | 是否已具备 |
| :--- | :--- | :--- |
| **记忆检索重排** | `score = lex + β·cos(s_t, s_memory)` | 已有 `/features` 与记忆向量 |
| **注入预算** | `s_t` 的稳定性 → 注入几条记忆 | 需新增阈值 |
| **回复长度/语气参数** | `s_t` → `max_tokens`、温度、正式度 | 纯运行时 |
| **该不该拒答** | `s_t` 的漂移 → 先验不确定 | 与验答门合并 |
| **人格状态** | `s_t` 跨会话持久化，作为实体状态 | 已有实例身份 + LTM |

**全部不经过词表。** 这是它与"小容量 transformer"的分界线。

## 三、审查：还有哪些地方在把它当 transformer

按代码逐个点名（2026-11-14 现状）：

| 位置 | 做法 | 性质 | 处理 |
| :--- | :--- | :--- | :--- |
| `serve_snn.complete_beam` | 树上束搜索出 top-k token | **词表运算** | 产品路径**不再调用** |
| `serve_snn.score_sequence` | teacher-forcing 的 log 概率 | **词表运算** | 仅评测用，产品不调 |
| `fusion/semprea_fuse.py` | `log q + α·log p` | **词表运算** | 保留为可审计机制，**默认 α=0 且不接入状态用途** |
| `semprea/serve.py` FusionDecoder | 逐 token 融合解码 | **词表运算** | 同上，代码保留、路径不启用 |
| `encode_texts`（`/encode`） | 各位置读出特征的**均值** | 半 transformer（句子嵌入） | 已有 `/features` 可绕开；`/encode` 降级为兼容接口 |
| `model.step` 的 `sensor_proj` | **加性电流**注入 | 输入接口 | 待改：门控式（增益调制），且这是唯一非词表通道 |
| 训练目标 | next-token CE | **transformer 目标** | 不改（已冻结），但**不能用它评估"状态好不好" |
| 指标 | top-1 / CE | **transformer 指标** | 状态侧改用：检索重排增益、拒答准确率、跨会话一致性 |

## 四、状态侧该量什么（替代 top-1）

1. **检索重排**：`s_t` 能否把正确记忆排得更高（对比词法基线）；
2. **拒答预测**：`s_t` 的漂移能否预测"这一问我答不了"（AUC）；
3. **跨会话一致性**：同一个人的同一类输入，`s_t` 的自相似是否高于不同类；
4. **时序敏感度**：改变输入的时间结构（间隔），`s_t` 是否随之改变——**这是唯一
   只有 SNN 才能通过、transformer 无法伪造的检验**。

第 4 条是关键：如果 `s_t` 对时间结构毫无反应，那它仍然只是个词袋。

## 五、不做的事

- 不改已冻结的权重；
- 不删融合代码（它仍是可审计的机制，只是不再是产品路径）；
- 不因为"状态侧指标更难"就回头去调融合算子。

## 六、状态侧第一测：自检索（2026-11-14）

用 `/features`（64 维投影后取均值）做记忆自检索，120 条、20–120 字的记忆：

| 条件 | top-1 | top-5 |
| :--- | ---: | ---: |
| gap_ms = 0 | **0.988** | 1.000 |
| gap_ms = 400 | **0.988** | 1.000 |
| 词法自检索（参照） | 0.316 | 1.000 |
| 随机 64 维（参照） | ≈0.008 | ≈0.04 |

**状态向量极具判别力**（0.988 对词法的 0.316）。

### 但这个数**不能**当成"检索变好"

自检索是"同一段文本找它自己"——任何确定性编码器都能做到，它测的是**判别性**，
不是**语义相关性**。真正的检索是"用一句提问去找那段记忆"，而那件事上 `/encode`
在 LoCoMo 上是 **hit@5 0.015**。

⇒ 正确的结论：**状态向量可判别，但尚未证明它可检索。**

### 另外一个观察

`gap_ms=0` 与 `gap_ms=400` 的自检索完全相同（0.988/0.988）——**时间结构改变了向量，
但没有改变它的判别力**。这是好事（说明时间通道不会破坏表示），也说明自检索这个
指标对时间不敏感，需要换一个更细的任务才能看出时间带来了什么。

### 过程记录

第一次跑出 0.000/0.000，因为我把相似度矩阵对角线抹成 −9 再查"自己是不是最大"——
**这个 bug 今天第三次出现**（`memory_health` 也犯过）。已加入检查清单：
**凡是"自己找自己"的检验，自己必须在候选里。**

### 半句 → 全句（比自检索难一档）

100 条记忆，用每条的前 60% 当查询去找完整的它：

| 方法 | top-1 | top-5 |
| :--- | ---: | ---: |
| **状态向量（`/features` 64 维）** | **0.865** | 1.000 |
| 词法（同样的查询） | **0.981** | 1.000 |

**状态向量比词法差 11.6pp。**

⇒ 这解释了 LoCoMo 上的 0.015：它的表示**可判别**（自检索 0.988），但**不擅语义**——
半句查全句这种"信息包含"关系，词法就够了且更好。

### 状态侧四条判据的最新状态

| 检验 | 结果 |
| :--- | :--- |
| 时序敏感度 | ✅ 通过（同 token 序列，插空步状态变 1.78/3.99） |
| 自检索 | ✅ 0.988（判别性强） |
| **半句→全句检索** | ❌ **0.865 < 词法 0.981** |
| 拒答预测 | 未测 |
| 跨会话一致性 | 未测 |

**结论（条件性）**：在"检索"这个用途上，状态向量**不如词法**。它的价值不在检索——
要找到它的价值，得去问它独有的那个维度：**时间**。

### 合成打字节奏：**状态完美解码时间标签（AUC 1.000）**

80 条记忆，随机附一个**与文本内容无关**的节奏标签（快 / 慢），慢的那些在用
`gap_ms=600` 计算特征。用状态的 mean/std/max（192 维）训一个线性分类器：

| 检验 | AUC |
| :--- | ---: |
| **状态能否解码节奏** | **1.000** |
| 对照：全部按同一节奏计算 | 0.529 |

**这是今天第一条全绿的读数**：时间标签被状态**完全解出**，而对照证明它不是从文本里
偷来的（0.529 ≈ 随机）。

## 这说明什么

- **时间通道有效**：不同的输入节奏确实写进了状态，而且写得非常清楚；
- **它与文本正交**：同样的文字，只改节奏，状态就可分；
- **transformer 做不到**：它对同样的 token 序列恒定输出。

## 但这仍然只是"通道可用"

标签是合成的——**它证明的是"能读"，不是"读到的有意义"**。
真实场景里"停顿长"可能意味着犹豫、回忆、情绪波动，也可能只是手离开键盘。

⇒ 下一步（唯一缺的一件）：**真实节奏 + 一个真实标签**。
最便宜的真实标签是"**这一问是否答不出来**"（拒答），它可以从现有的验答结果里生成。

### 大规模合成：**时间带来了文本没有的信息（AUC +0.12）**

600 个样本，标签是**文本与节奏的合取**：`(文本含"天气"或"我") AND (节奏慢)`。
这个设计的用意：**只靠文本最多各猜一半**。

| 输入 | 留出 AUC |
| :--- | ---: |
| **仅文本**（gap 全 0） | **0.793** |
| **文本 + 真实节奏**（gap 按标签 0 / 600ms） | **0.913** |

**差 +0.12 AUC。**

因为标签是合取，文本只能提供一半的信息，理论上限压在 0.79 附近；加上节奏才可能到 0.9 以上。
实测正好落在那里 ⇒ **节奏带来的不是冗余，是文本里没有的那一半。**

配合上一步（状态对节奏的解码 AUC 1.000、对照 0.529）：
**时间通道不仅能读，而且读到的东西有独立的预测力。**

## 这是今天第二条全绿

1. 节奏可解码：AUC 1.000（对照 0.529）；
2. **时间带来独立信息：AUC 0.793 → 0.913**。

两条都在**词表之外**——这正是前面四个融合算子都到不了的地方。

**限定**：标签仍是合成的。它证明的是"通道有效且信息独立"，不是"真实停顿有语义"。

## 七、加性 vs 门控：**影响幅度没有区别**

给 `TokenEProp` 加了 `sensor_mode`（`add` 默认 = 现行，`gate` = 乘 `(1+调制)`）。
同一段文本、同一个随机 `sensor_proj`、c 取全 +1 与全 −1：

| 模式 | 特征最大差 | 特征范数 |
| :--- | ---: | ---: |
| `add`（加性） | 1.2347 | 59.72 |
| `gate`（门控） | **1.2347** | 54.28 |

**影响幅度完全相同**（1.2347 vs 1.2347），只是整体状态不同（范数 59.72 vs 54.28）。

⇒ 在当前的权重尺度下，**门控并不比加性"更有效"**——它改变的是基线，不是通道的灵敏度。
这与"加性电流太窄"这个猜想不符：换成乘法没有放大信号。

**这仍然是条件性结论**：只测了一个随机 `sensor_proj` 尺度；不同尺度可能不同。

## 八、输入编码：**仍未解决**

token 进来仍然是 `emb(32000×256)` 查表 + `proj(256→7812)` 加性电流——**与 transformer 同构**。

`gap_ms` 只是在 token **之间**插空步，token 本身怎么变成脉冲没变。真正的"自己的编码"
（首脉冲延迟 / 秩序编码 / 群体速率编码）一条都没实现。

**这是"把它当小 transformer 用"最根的一处，今天没动。**

## 九、时间编码接进模型：**首测没有差别，接线可疑**

把 `spike_encoding.encode()` 的帧逐帧喂给 `model.sensors`，与"每次都喂完整向量"对比：

| 注入方式 | c1 vs c2 的特征最大差 |
| :--- | ---: |
| 一次性加性注入 | 0.7951 |
| **时间编码（首脉冲延迟）** | **0.7951** |

**两者完全相同（到小数第 4 位）**，这不正常。

已知同一模型**对空步敏感**（同 token 序列插空步，特征差 1.78 / 3.99），
所以"模型对输入时刻不敏感"这个解释站不住——**更可能是我这段接线没生效**：
逐帧赋值 `model.sensors` 后，`step()` 里读到的可能仍是同一份张量，
或者帧的非零值恰好落在没有输入的步上。

**按纪律：不作结论。** 下一步必须先验证"逐帧的 sensors 确实被 step 读到"
（打印每步实际用的向量），再谈可分性。

## 今天这条线的状态

| 项 | 状态 |
| :--- | :--- |
| 编码器实现 | ✅ 3 条守卫（首脉冲、单次发放、顺序可分辨） |
| 噪声：逐样本归一化会伪造信息 | ✅ 已修（改固定量程） |
| 接进模型 | ⚠️ **接线未验证**，首测无可测差别 |
| 对主网络的影响 | ❌ 未测（需要在接对之后） |

### 接线已验：**不是 bug，是真的没有差别**

用 spy 打印每一步 `step()` 实际收到的 `model.sensors`：

```
编码帧（每步非零通道数）: [1, 14, 1]
step 实际收到:            0.9, 7.2, 0.2     ← 逐帧确实不同
```

⇒ **逐帧赋值被正确读取。** 上一测"两种注入结果完全相同"不是接线错。

原因是**总量相同**：一次性注入每步 8.3，时间编码三步合计也是 8.3
（0.9+7.2+0.2）。于是差别**只在分布**，而在这 3 步窗口里、τ∈{2,128} 下，
读出对分布不敏感——总电荷主导。

**条件性结论**：在这套注入与三步步长下，首脉冲延迟编码**没有提高可分性**。
要让它有意义，需要满足其一：
- **更多步**（编码窗 ≥8，让延迟真正拉开）；
- **更小的 τ**（让早到的脉冲占更大权重）；
- **注入位置改变**（现在是加性电流，会累加；门控/突触式注入不会）。

这三条都还没测。

### 三条条件一起试：**没有一条提高了可分性**

14 个 token、编码窗 8 步、c1 与 c2 只在通道 0/1 上互换（0.95↔0.05）：

| 模式 | 注入 | c1 vs c2 特征最大差 |
| :--- | :--- | ---: |
| add | 一次性 | **1.1951** |
| add | 时间编码 | 0.7951 |
| gate | 一次性 | 0.7951 |
| gate | 时间编码 | 0.7951 |

**三条待测条件——更多步、更小 τ（用 8 步窗口代替 3 步）、门控——都没有提高可分性。**
反而在加性模式下，时间编码把 1.1951 降到了 0.7951。

### 条件性结论（这次是完整的）

在**冻结的主网络 + 加性/门控电流注入 + 读出 EMA**这套结构下，
**首脉冲延迟编码不提高特征层面的可分性**。三条候选机制都试过。

**但要注意指标的局限**：这里量的是"最大特征差"，不是"分类器能否分辨"。
分布变了、最大差变小，分类性能未必变差。**要下最终结论，需要一个线性分类器的 AUC，
而不是逐元素最大差。** 这一步没做，因为今天的上下文用尽了。

下一件的顺序写死：
1. 用分类器 AUC 重测（同一批数据，四个条件）；
2. 只有在 AUC 也不提高时，才写"时间编码在这套结构下无效"。

### 用分类器 AUC 重测（100 样本，标签 = 通道0 > 通道1）

| 模式 | 注入 | 留出 AUC |
| :--- | :--- | ---: |
| **add** | **一次性** | **0.810** |
| add | 时间编码 | 0.452 |
| gate | 一次性 | 0.335 |
| gate | 时间编码 | 0.398 |

**结论明确：一次性加性注入 0.810 最好；时间编码 0.452、门控 0.335——都把它打坏了。**

上一轮用"最大特征差"看不出方向，用 AUC 一看就清楚了：**这不是"没提高"，是"显著变差"。**

### 为什么——这才是最根本的一条

**主网络是在"稠密、加性、每步都有输入"的方式下训出来的。** 任何改变注入方式的尝试
（时间编码、门控）都让它工作在**分布之外**。

⇒ 这不是"时间编码不好"，是**编码与网络是一起训出来的，不能单独换一个**。
冻结权重 + 换编码 = 必然退化。

### 于是"输入编码"这条的完整结论

| 尝试 | 结果 |
| :--- | :--- |
| 时间编码（首脉冲延迟） | AUC 0.452（加性）/ 0.398（门控）|
| 门控注入 | AUC 0.335 |
| **一次性加性（现状）** | **0.810** |

**要让它自己做编码，必须重训主网络**——而这与"权重冻结"直接冲突。
这是今天所有尝试里，唯一一条**明确指向"必须重训"**的证据。

## 十、其余五条矛盾的现状（2026-11-14）

| 矛盾 | 现状 | 冻结权重下能做吗 |
| :--- | :--- | :--- |
| **稀疏：付稠密代价收脉冲噪声** | 每步全量 matmul | ✅ **能**。实测 z 非零比例 **20.7%**（13 步，0.077–0.277）⇒ 读出 15,624 行里平均只需 3,236 行，**可跳过 79.3%** |
| **时间：数 token 不数时间** | 已部分解决 | ◐ 空步注入已做（状态差 1.78/3.99、节奏 AUC 1.000、独立信息 +0.12）；但 τ 仍以步为单位，**彻底解决要重训** |
| **读出：softmax 硬接** | 仍在词表上 | ✅ 能：状态侧用途（检索/拒答/一致性）**完全不需要这个词表读出** |
| **同步：全局时钟** | 每步全体更新 | ❌ 改异步要重写推理框架，且权重按同步训出来 |
| **训练：局部学习没用上** | 离线训完冻结 | ❌ DFA 实测对齐 0.32，不足；在线学需要可训 |
| **指标：top-1 是 transformer 的** | — | ✅ **今天已经换了**：AUC、自检索、半句检索、时序解码 |

### 结论

**六条里三条可以在冻结权重下做，两条不行，一条已经开始。**

- **可做且未做**：稀疏推理（79.3% 可跳过）——这是唯一一条**纯工程、收益可量化、
  且完全符合 SNN 本意**的优化；
- **已做**：指标（换成 AUC/检索/时序）、读出（状态侧绕开词表）、时间（部分）；
- **不行**：同步（权重按同步训）、局部学习（DFA 不足）。

### 更正：稀疏能跳过的不是 79.3%，是 **36.9%**

上表用 `z`（脉冲）算的 79.3% **测错了对象**——矩阵乘的输入不是脉冲，是**读出特征**。

同一段文本实测：

| 量 | 非零比例 |
| :--- | ---: |
| 脉冲 `z` | 20.7% |
| **读出特征 `features`**（matmul 的真正输入） | **63.1%** |
| 可跳过 | **36.9%** |

原因：读出是两个指数移动平均，**EMA 会把稀疏脉冲在时间上摊开** ⇒ 特征变稠密。
脉冲稀疏 ≠ 特征稀疏。

### 而且这条路本仓已经量过，是负的

`AGENTS.md` 记录过 A1 候选剪枝：**gather `w_out[:, cols]` 实测慢 25 倍**——
访存受限，而稠密 matmul 走 tensor core。同样的道理适用于这里：
**15624 维里跳掉 36.9%，用 gather 实现大概率比稠密还慢。**

⇒ **稀疏推理在本仓的既有证据下不成立**（36.9% 的额度 + gather 慢 25 倍的先例）。
要真兑现稀疏，得是**结构化稀疏**（整块跳过）或**更小的读出宽度**，不是逐元素跳。

## 十一、用 Rust/原生重写慢的部分，值不值

先量清楚慢在哪。**推理每步实测 1.496 ms**、每步主要 FLOP 只有 `proj(256×7812) ≈ 4.0 MFLOP`
⇒ 等效 **2.67 GFLOPS**。单核稠密 matmul 通常 5–30 GFLOPS ⇒ **有 2–10 倍的头**。

但要分两个场景，结论相反：

| 场景 | 瓶颈 | 原生重写有用吗 |
| :--- | :--- | :--- |
| **训练（batch 256）** | 大 matmul | ❌ 已实测：Triton 融合整条逐元素链只占一步的 **2.6%** |
| **推理（batch 1）** | **Python 调度 + 小张量开销** | ✅ 2.67 vs 5–30 GFLOPS，**有 2–10 倍空间** |

### 但先别写 Rust——有一条更便宜的

本仓 T4 实测过 `torch.compile`：

| 配置 | eager | compile | 比 |
| :--- | ---: | ---: | ---: |
| B=64、N=1024 | 58.1 ms | 23.4 ms | **2.48×** |
| B=256、N=4096（训练工作点） | 21,356 tok/s | 4,037 tok/s | 0.19×（慢 5.3 倍） |

**compile 在"小配置"上赢 2.5 倍、在"大配置"上输 5 倍。而推理正是 batch=1 的小配置。**

⇒ 顺序应当是：**先试 `torch.compile`（半小时，可能直接拿 2.5×）**，
拿到之后再看还剩多少，再决定要不要动 Rust。

### Rust 真正值得动的地方（如果 compile 不够）

只有一处：**把 256 步的 Python 循环压成一个原生调用**（`for step in range(n): model.step(...)`）。
这是纯调度开销，Rust/C++ 的 pyo3 绑定或一个自定义算子都能做，且**不改数值**。

其余地方（matmul、树读出）没有意义——它们是 BLAS 或 tensor core 的活。

### `torch.compile` 在本机**跑不起来**：缺 C++ 编译器

```
InductorError: InvalidCxxCompiler: Compiler: cl is not found.
```

`torch.compile` 的 Inductor 后端要 MSVC 的 `cl.exe`，本机没有。**这不是 torch 的问题，
是缺 Visual Studio Build Tools。**

| 路径 | 代价 | 预期 |
| :--- | :--- | :--- |
| 装 MSVC Build Tools，再试 compile | 下载 ~2–6 GB | 本仓实测小配置 **2.48×** |
| 直接写原生循环（pyo3 / 自定义算子） | 1–2 天 | 2–10×，但**只省调度**，不改 matmul |
| 不动 | 0 | 1.170 ms/步（eager 实测） |

**先装编译器试 compile 是性价比最高的**：它不需要改代码，而且本仓在同族配置上
已经量到 2.48×。

（注：`eager` 这次测到 1.170 ms/步，比上一次的 1.496 ms 略低——同一台机、同样 41 步，
差异来自负载。做基线比较时要用同一次运行的数。）

### `torch.compile` 通了：**1.39×**（关键是先加载 MSVC 环境）

`cl.exe` 其实装了，只是不在 PATH。用 `vcvars64.bat` 之后 compile 正常：

| | ms/步 |
| :--- | ---: |
| eager | 2.010 |
| **compile** | **1.449** |
| **加速** | **1.39×** |

（同一批运行内比较；eager 跨次在 1.17–2.01 之间波动，受负载影响，**只能比同一批的数**。）

比训练配置上的 2.48× 低——推理是单样本、逐 token，图更小，Inductor 能融合的少。

### 落地要解决的一件事

`torch.compile` 需要**编译期环境**（vcvars）。服务器上不能要求用户先跑 `vcvars64.bat`，
所以要么：
1. 首次启动时用 `subprocess` 先 `call vcvars64.bat` 再起服务；
2. **预热后把 Inductor 的缓存目录随包分发**（`.cache/torch/inductor`），之后不再编译。

第 2 条更好：用户侧零依赖。缓存与平台绑定，所以运行层本来就是**按平台另发**的。

### 关于原生循环

compile 已经拿掉了一部分调度开销（1.39×）。剩下的 2–10× 要靠原生循环，
但它**不改 matmul**，收益上限就是调度那部分。**在 compile 落地之前不建议动 Rust。**

### 端到端验证：compile 在真实端点上也是 **1.4×**

同一个服务、同一段文本（56 token），eager 与 compile 各起一个进程：

| 端点 | eager | compile | 加速 |
| :--- | ---: | ---: | ---: |
| `/features` | 0.221 s | **0.160 s** | **1.38×** |
| `/complete` | 0.119 s | **0.081 s** | **1.47×** |

与单步的 1.39× 一致 ⇒ **收益不只在微基准上，端到端拿得到**。

编译预热约 1 分钟（一次性，可随包分发 Inductor 缓存）。

### 于是原生循环的最后判断

compile 之后 `/complete` 已经到 **81 ms**。要判断还剩多少调度开销，需要把"一步里
matmul 占多少、调度占多少"分开——这个数还没测。**在它出来之前不动 Rust**：
剩下的是不是调度开销，目前没有证据。

### 一步里 matmul 只占 **5.8%**——原生循环现在有证据了

| 成分 | 耗时 |
| :--- | ---: |
| `proj` matmul（1×256 @ 256×7812） | **53.1 µs** |
| 完整一步 | **2047.9 µs** |
| **matmul 占比** | **5.8%** |
| 调度 + 其余张量操作 | **94.2%** |

**这推翻了"python 开销不是瓶颈"的暂定判断。** 之前引用的"逐元素链只占 2.6%"来自
**训练工作点（batch 256）**——那里的 matmul 很大。**推理是 batch 1，完全相反。**

⇒ **原生循环（Rust/pyo3 或自定义算子）现在有明确依据**：上限是 ~17×，
现实目标取 3–5× 合理。而且它**不改数值**，可以逐位对照验证。

### 下一步的落地形状

1. 把 `model.step` 的整条逐元素链写成**一个原生函数**（入参：token、trace 的各个张量；出参：更新后的张量）；
2. 逐位对照 eager 的结果（这是硬判据，不是"看起来对"）；
3. 再比延迟。

### 原生内核的工具链**已验证可用**

用 `torch.utils.cpp_extension.load_inline` + 本机的 MSVC（`vcvars64.bat`）：

```
C++ 扩展可用，1000 次 0.006s          → 6 µs/次
逐位相同: True
```

**两件事同时成立**：编译链通、且**结果与 PyTorch 逐位相同**。

⇒ 下一步（把 `model.step` 的整条逐元素链写成一个 C++ 函数）不再有工具链风险，
只剩"把数学搬过去 + 逐位验证"这一件事。

### 已知的落点（按收益排）

一步 2047.9 µs 里，matmul 只占 53.1 µs。剩下 ~1995 µs 分散在：
张量创建（每步 `torch.tensor([id])` 两次）、约 20 个逐元素算子、广播与 `where`。
C++ 侧这些都是裸循环，且可以**一次调用完成整步**，把 Python→C++ 的边界从 20 次降到 1 次。

**现实目标：3–5×**（17× 是理论上限，受限于内存带宽与 trace 的张量数量）。

### 判据（写死）

1. **逐位相同**：同一 token 序列、同一初始 trace，C++ 与 PyTorch 的 `v/z/refractory/readout`
   必须逐位相等；
2. 端到端 `/features` 与 `/complete` 各测三次取中位；
3. 不改任何数学。

### 热点还没找到：三个假设都排除了

| 假设 | 实测 | 占 2047.9 µs |
| :--- | ---: | ---: |
| matmul（`emb[tok] @ proj`） | 53.1 µs | **5.8%** |
| 学习痕迹（eps_in 整表乘 + scatter + eps_rec 乘） | 17.7 µs | **1%** |
| 其余逐元素链（~10 个 7812 维算子） | 未逐个测，量级 ~10–50 µs | 个位数 % |

**三项加起来不到 10%，剩下 90% 没有归属。**

⇒ **现在还不能写 C++ 内核**——不知道要搬什么。先把一步内部**逐段计时**（在 `step` 里插
计时点，或把各段单独跑一遍），找到真正的大头，再决定搬不搬、搬哪一段。

这与今天反复出现的教训是同一个：**在没定位到热点之前动手，等于赌。**

### 已知的下一步

1. 在 `step` 内部插 6–8 个计时点（token 构造、emb gather、proj matmul、recurrent、sensor、
   阈值/发放、复位、readout EMA、痕迹），一次运行就能看到分布；
2. 只搬占比最大的那一段；
3. 逐位对照。

### 逐算子剖析（100 步，总 179.7 ms ⇒ **1.797 ms/步**）

| 算子 | 占比 | 调用次数 | 单次 |
| :--- | ---: | ---: | ---: |
| `aten::mm` | 17.1% | 100 | 308 µs |
| `aten::mul` | 11.4% | 1,100 | 25.8 µs |
| `aten::index_select` | 11.0% | 500 | 45.7 µs |
| `aten::scatter_add_` | 10.2% | 200 | 91.4 µs |
| `aten::_to_copy` | 4.2% | 1,800 | 8.0 µs |
| `aten::copy_` | 3.0% | 1,900 | 2.8 µs |
| `aten::add` | 2.9% | 700 | 7.6 µs |
| `aten::where` | 2.8% | 500 | 11.7 µs |

**前八项合计约 62%，没有任何单一算子超过 20%。**

### 这个分布推翻了"94% 是调度开销"

- 之前用"一步 2047 µs − matmul 53 µs"推的 94% 是**减法得到的残差**，不是实测的调度；
  辨析器显示 matmul（`mm`）实际占 **17%**，且大量时间分散在 8 个以上的小算子里；
- **没有一个大头可以单独搬**。C++ 融合能吃掉的是"相邻逐元素算子的合并"，
  按这个分布，现实收益更接近 **1.5–2×**，不是 3–5×。

### 一处仍值得单独做

`scatter_add_` + `index_select` 合计 **21%**，都是 32000 宽的 gather/scatter。
其中 `scatter_add_` 是 `eps_in`（学习用的资格痕迹）——**推理时 `update=False` 根本不需要它**。
跳过它预计能省 **10–15%**，而且不需要写 C++。

**下一步顺序**：先做这个纯 Python 的跳过（便宜、可逐位验证），再评估要不要动 C++。

### 跳过学习痕迹：**改是安全的，但没有测到加速**

改动：`update=False` 时不再更新 `eps_rec` / `eps_in`（它们只服务于学习，
不影响 `v / z / refractory / readout` 这四件推理真正用的状态）。

| 量 | 值 |
| :--- | ---: |
| 改后每步 | **2350 µs** |
| 改前每步 | **1797 µs** |
| 比 | **0.76×（更慢）** |
| `eps_in` 是否仍为零 | ✅ 是（跳过生效） |

**但 0.76× 不能当结论**：eager 在同一台机、同样规模下实测过 **1.17–2.05 ms** 的跨次波动，
2350 落在波动范围内。**这次测的是噪声，不是差异。**

### 判据问题

要判定这个改动值不值，必须**同一进程内 A/B**（先跑原实现若干步计时，再打补丁跑若干步），
而不是跨进程、跨次比较。

### 改动本身保留

它是安全的：`update=True` 的分支与原来逐字相同，推理侧只少了两个不被使用量的更新。
**但不宣称它带来了加速**——目前没有证据。

### 同进程交替 A/B：跳过学习痕迹 **1.00×（零差异）**

三次交替（跳过 / 保留 / 跳过 / 保留 …），各 300 步：

| 臂 | 中位 |
| :--- | ---: |
| 跳过痕迹 | **1455 µs** |
| 保留痕迹 | **1461 µs** |
| 比 | **1.00×** |

（第一次 2427 µs 是预热离群，落在中位数之外。）

**结论：跳过学习痕迹没有带来任何可测的加速。** 剖析里 `scatter_add_` 的 10% 是
**带剖析器开销的读数**，去掉剖析器后该项在总时间里几乎不可见。

### 这条同时给出了今天缺的那个工具

**同进程交替 A/B** 是唯一能穿越跨次漂移（1.17–2.05 ms）的比法。
今后所有性能改动都用它，不用跨进程的数。

### 开关保留但不启用

`skip_learning_traces` 默认 `False`（训练路径与原来**逐字相同**），可在推理时打开；
**没有证据说它快**，只是无害。

## 十二、更正：「局部学习一次没用上」这句话是错的

我此前写过"训练：整个局部学习的优势一次没用上"。核查代码后**必须更正**：

```
model.py : .backward() 出现 0 次
run_1b.py: .backward() 出现 0 次
```

V1 的主网络**就是用纯局部规则（逐时刻 e-prop）训出来的**，全程无 autograd。
**局部学习在训练时是用上的。**

### 真正没用上的是另一件：**部署时的在线适应**

模型训完就冻结，部署期间不再学习。而"本地规则"的独特优势恰恰在这里——

| 场景 | 用没用局部规则 |
| :--- | :--- |
| 训练主网络 | ✅ 用了（e-prop，无 autograd） |
| **部署时随使用而更新** | ❌ **一次没有** |
| 训 `sensor_proj` | ⚠️ 用了 DFA（**不是纯局部**，是全局误差广播） |

所以那条矛盾的正确表述是：**我们在训练时享受了局部性（不需要 BPTT），但没有在部署时
享受它（模型不会随用户变）。**

### 这个优势能不能兑现——可测的形状

唯一能证明"在线局部适应有用"的实验是：**同一份冻结权重，一个臂在部署流上持续用
局部规则更新一小块，另一个臂冻结，比下游指标。**

最小版本：在冻结的读出上挂一个**纯 Hebbian 的在线层**（无误差回传），
在用户真实流（记忆库按时间顺序）上跑，比"该流上的预测质量"。
判据：在线臂在**后段**优于冻结臂，且前段不劣化。

**这条不需要重训主网络**，10M 小模型训练完可以直接拿它做。

## 十三、真正的纯局部激素调控：**用脑区特化给出受体结构**

### 为什么 DFA 只有 0.32

DFA 的反馈是一个**随机矩阵** B（64 × 15624）。它把输出误差"撒"回全部神经元，
但没有任何结构说明"哪个区域该对哪种误差敏感"。余弦 0.32 就是这个**无结构**的代价。

### 生物上是怎么解决的

激素是**全局广播**的（多巴胺、乙酰胆碱……），但**每个脑区表达不同的受体**——
同一个激素在不同的区域产生不同的可塑性调制。**全局信号 + 区域受体 = 有差别的信用分配，
而整个过程没有反向传播。**

### 落到本仓的形状

A1 已经有**脑区特化**的基础设施（8 区 × 1,024、区内偏置）。把它接上：

```
激素向量 h ∈ R^d          （d≈4–8：误差、新奇、唤醒、节律）
     ↓ 全局广播（同一个 h 发给所有区）
区 r 的受体 ρ_r ∈ R^d      （每个区自己学）
     ↓
突触 (i,j) ∈ 区 r：Δw = η · (h · ρ_r) · pre_i · post_j
```

**三件事都纯局部**：
1. `h` 从读出端的预测误差、发放率偏离、输入新奇度算出来——都在本地；
2. `ρ_r` 用区内信号自己更新（`Δρ_r = η_ρ · h · 该区近期的预测贡献`）；
3. 突触更新只用 pre/post 与一个标量 `h·ρ_r`——**没有一条跨层的误差路径**。

### 为什么它能超过 DFA

DFA 的 B 是**随机且固定**的；这里的"有效反馈"是 `h ⊗ ρ`——**低维、结构化、可学**。
d=8 的激素、K=8 的区域 ⇒ 有效路由只有 **64 个自由度**，而 DFA 的 B 有 100 万。
**用小得多的自由度去近似真实雅可比，在样本少的时候反而更准**（与"小模型在少数据上更好"同源）。

### 判据（写死）

1. **对齐度**：用有限差分量 `h⊗ρ` 与真实梯度的余弦，必须 **> 0.6**（DFA 是 0.32）；
2. **端到端**：在合成节奏任务上，`h⊗ρ` 臂的 AUC 必须高于 DFA 臂；
3. **纯局部检查**：代码里**不许出现 `.backward()`**（这是硬性守卫，与主网络同一条）。

## 十四、三臂完全相同（0.109）：**sensor_proj 从来没有更新路径**

在**可训练**条件下重做（从零训练 1500 步、真实树读出、语义化任务、传感器从第一步就在）：

| 臂 | 留出 top-1（10 类，随机 0.10） |
| :--- | ---: |
| `zero`（不给传感器） | **0.109** |
| `add`（加性） | **0.109** |
| `gate`（门控） | **0.109** |

**三臂到小数点后三位完全相同。**

### 根因是一个代码事实，不是能力界限

```
grep sensor_proj model.py
331:  self.sensor_proj = None
339:  self.sensor_proj = torch.zeros(...)   ← 零初始化
520:  if ... self.sensors is not None:
523:      modulation = self.sensors @ self.sensor_proj
```

**`sensor_proj` 只被读，从来没有被写过。** e-prop 的更新覆盖 `w_in` / `w_out` / 树，
**不含 `sensor_proj`**。

⇒ 三臂相同是必然的：通道在训练里也是死的。

### 这条把整条线的根钉住了

之前所有"传感器学不出"的结论（冻结权重下的 DFA、余弦 0.32、AUC 0.7629），
**共同的根因就在这里**：这个通道从来没有接入学习规则。

所以要检验它，缺的不是数据、不是编码、不是门控——**是给 `sensor_proj` 一条更新规则**。
这也正是"脑区受体 × 全局激素"设计要解决的那一件事：**用低维、可学、纯局部的路由，
给这条通道一条真正的信用分配路径**。

## 十五、给 `sensor_proj` 接上第一条更新规则（激素三因子）

在 `step()` 里、树给出 `tree_signal` 之后：

```
Δsensor_proj[i,j] = η · h · c̄[i] · z̄[j]      h = tree_signal 的均值（标量激素）
```

**纯局部**：前 = 本批传感器均值、后 = 本步平均发放、调制 = 树的标量信号；
**没有 `.backward()`、没有跨层误差路径**（与主网络同一条纪律）。

### 接线已验：更新确实在发生

```
初始 sensor_proj 范数 0.0
20 步后            0.028
```

⇒ **通道第一次有了写路径。** 之前它是"只读不写"，这正是所有"传感器学不出"的共同根因。

### 但任务指标仍停在随机水平

1500 步 `add` 臂：top-1 **0.109**（随机 0.10）。所以：

- 通道**能被训练**（范数在涨），
- 但**训练信号太弱**：0.028 的范数作用到 7812 维电流上，还撬不动输出。

### 下一步（两条，按代价）

1. **放大 `lr_sensor`**（0.05 → 0.5/2.0）并观察范数与 top-1 是否同步动——最便宜；
2. **换更强的激素**：现在用 `tree_signal` 的**均值**（一个标量）；按脑区受体设计，
   应该用**逐区向量**，让不同区对同一个激素给出不同增益。现在这个模型没有区结构
   （n_rec=156 单块），要做就得先分区。

**判据不变**：三臂必须分开（不能都是 0.109）。

## 十六、0.109 这个数**在所有配置下都不变**——评测本身是退化的

换了四种配置，top-1 **每次都精确等于 0.109**：

| 配置 | top-1 |
| :--- | ---: |
| lr_sensor 0.05、零初始化 | 0.109 |
| lr_sensor 0.5 | 0.109 |
| lr_sensor 2.0 | 0.109 |
| 改用协方差更新 | 0.109 |
| `zero` 臂（根本不给传感器） | 0.109 |

**一个数在所有条件下不变，说明它不是"测出来的"，是常数。** 最可能的解释：
模型对十个数字的输出几乎恒定（树读出的偏置主导），argmax 永远是同一个数字
⇒ top-1 就等于"那个数字在目标里出现的频率"≈1/10，采样噪声给出 0.109。

⇒ **不是三臂没差别，是这个评测分辨不出差别。**

### 中途修掉的两处真实错误（记下来）

1. **`sensor_proj` 从来没有写路径**——这是所有"传感器学不出"的真正根因（已修，范数 0→0.028 验证）；
2. **更新用了"批均值的外积"** 而不是协方差——秩 1 常数矩阵，每步几乎相同，
   学不到样本间的对应关系（已改为 `c̄ᵀz̄/B` 的去均值叉积）。

### 下一步（必须先修评测，再谈结论）

用**训练过的线性头**替代树读出做 10 类判别（前面合成实验里，训过的头能到 0.87，
而随机头只有 0.096）。**在评测能分辨之前，任何"三臂相同"都不能读成"通道无效"。**

## 十七、换成拟合的线性头后，**仍是 0.109**

把评测从"树读出"换成"在训练特征上闭式拟合的岭回归头"（能表达这个任务），
`add` 臂 1500 步：**top-1 仍为 0.109**。

⇒ **评测退化的解释也不成立。** 换成能表达任务的头，结果一点没变。

### 那就只剩一个解释

**特征里没有温度信息。** 传感器经 `sensor_proj` 加到电流上的那点量，
在 7812 维的文本驱动电流面前可以忽略——**不是头分辨不出，是信号不在特征里。**

这与范数观察一致：`sensor_proj` 训练后也只有 1e-2 量级，而文本路径的电流是 O(1)。

### 于是这条线的结论（条件性，写清 setup）

在 **15M 模型、1500 步、lr_sensor ≤ 2、协方差三因子规则、语义化温度任务** 下，
**传感器通道没有把信息送进特征**。

**未测**：
- 更长的训练（1500 步对 7812×16 的通道可能远不够）；
- 把 `sensor_proj` 初始化成非零（零初始化 + 弱梯度是慢启动）；
- 门控式注入（今天只测了加性）；
- 更大的传感器通道宽度 / 直接投影到读出维度。
