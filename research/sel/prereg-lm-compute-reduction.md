# 预注册：算法降算力——候选剪枝 + 低秩（2026-11-10）

**状态：判据先落盘。**

## 理由

1B 的账：每 token **~1.8 GMAC**（= 9·N·V，K=4），20B token 在 10 TFLOPS 下 **83 天**。
工程优化（T1–T5）提利用率，这一轮降**每 token 的算术量**。

参考 DeepSeek：V3 的 MoE/MLA/MTP/FP8；**V4.1 Flash 的 Engram（巨型稀疏查表）与 CSA2 分层 indexer
（先剪候选再算）**——后者直接对应我们的 V 维度。

## 设计

**A1 bigram 候选剪枝**：对每个位置，用 bigram 表取**频次最高的 C=256 个候选**，训练时把 target
强制放进候选；softmax 与 NLAL 更新只在这 C 列上做。**评测仍在全词表上算 top-1**（唯一可比口径）。

**A2 低秩输入嵌入**：`w_in = E(V×d)·P(d×N)`，d=256。更新仍是两段局部乘积（E 用 `eps_in`，P 用 `post@P^T`）。

**A3 低秩读出**：`w_out = A(M×r)·B(r×V)`，r=512，B 固定随机、只学 A。

**A4 MTP**：每位置预测后 2 个 token。

**A5 FP8/FP4** 权重。

## 判据

| # | 门槛 | 不过怎么办 |
| :--- | :--- | :--- |
| **A1-0** | 候选表 = 全词表（C=V）时与现路径**逐位一致**（1e-6） | 实现有误，修 |
| **A1-1** | **target 命中候选的比例 ≥95%** | C 提到 512/1024；仍不足则加一元频率兜底 |
| **A1-2** | 全词表 top-1 掉 **≤1pp**（对照 P1 的 0.2973） | C 提到 512 |
| **A1-3** | tokens/s **≥5×**（同一 batch 下与全量 softmax 比） | 不上 |
| **A2-1** | top-1 掉 ≤1pp | d 提到 512 |
| **A3-1** | top-1 掉 ≤1pp | 不做（A1+A2 已到 19×） |
| **A4-1** | 固定 token 预算下 top-1 提升 ≥1pp | 不做 |
| **A5-1** | 与 bf16 的 top-1 差 ≤0.5pp | 不做 |

**执行顺序写死**：**A1 的 A1-1/A1-2/A1-3 全过之前，不碰 A2–A5。**

## 2026-11-10 实测补注：**A1 先跑，结果慢 25 倍；顺序改为 A3 优先**

KdConv、`--candidates 256`、50 次更新跑了 **>10 分钟**；稠密路径是 **0.47 秒/更新** ⇒ **慢约 25 倍**。

**不是实现 bug，是结构**：候选版每步要 `gather w_out[:, cols]` = 4096×16×256 = **16.8M 个浮点（67 MB × 2 次）**，
**访存受限**；而稠密版是一次 197 MFLOP 的 matmul，**走 tensor core**。

⇒ **候选剪枝只在 V 远大于 C × 张量核加速比时才可能划算**。V≈3,000 时它只有坏处。
**执行顺序改为：A3（低秩读出）优先**——它降的是 **M**（1B 配置下 160,000，是 `M×V` 里的主导项），
而且全程是稠密 matmul。A1 的代码保留（守卫齐全），标为"**实测更慢，勿用**"。

## 2026-11-10 实测：A3 低秩读出 **2.0×**（不是 FLOP 比的 5×）；batch 256 **10.5×**

`bench_train.py`，N=4096、V=3001、4 个 τ：

| 配置 | batch 64 | batch 256 | 参数量 |
| :--- | ---: | ---: | ---: |
| 稠密读出 | 8,462 tok/s | 19,987 tok/s | 61.5M |
| **低秩 r=512** | **15,781 tok/s** | **40,586 tok/s** | **22.2M** |

- **A3 实测 1.86×（batch 64）/ 2.03×（batch 256）**；参数 **2.8× 更少**。
  纯 FLOP 比是 5×（49.2M vs 9.9M MAC/token），**墙钟只拿到 2×**——因为每一步不只有 matmul，
  Python 与内核开销仍占一半以上；
- **batch 16 → 256 是 10.5×**（N=1024：5,451 → 57,359 tok/s），每更新耗时几乎不变（91 → 138 ms）
  ⇒ **瓶颈确实是每步调度，不是算力**；
- **两者相乘**：N=4096 上 2,188 → **40,586 tok/s = 18.5×**（同型号、同代码路径）。

⇒ 1B 的账要重算：按 18.5× 折算，20B token 从 ~190 天降到 **~10 天**（还不含 bf16 与编译）。
**"边缘不可行"这个判断因此要改成"取决于 T3+T4 还能不能再叠 3–5×"**——这条留待实测。

## 2026-11-10 实测：T3（bf16 矩阵乘）在当前规模**没有收益**（−3%）

N=4096、V=3001、batch 256、A2+A3 全开：**53,219 → 51,569 tok/s**（−3%）。

原因不是实现错，是**这个规模下矩阵乘根本不是瓶颈**——每步的开销主要是内核启动与逐元素运算，
而 bf16 还要多做两次 cast。

⇒ **T3 是"规模条件收益"**：1B 配置下 matmul 大约大 100 倍，那时 bf16 才会兑现。
**在当前实验规模上不启用**（`--amp` 默认关），等 1B 探针时再开。

## 已知的代价与边界

- 候选剪枝**有偏**：长尾字永远进不了候选 ⇒ **CE 不再与全量版可比，只认全词表 top-1**；
- 索引器是**静态 bigram 表**（不是学出来的 router）——比 DeepSeek 更干净，代价是长尾覆盖；
- 低秩嵌入/读出改变模型类，必须与全秩并排对照；
- 数字以实测吞吐为准，不用理论峰值外推。

## 成本

A1 实现半天 + 1 臂（16k 步，~2h）；A2 半天 + 1 臂；A3–A5 视 A1/A2 结果。
