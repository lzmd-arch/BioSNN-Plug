# 仲裁器：跨规则冲突检测与权重调节

[English](README.en.md) · [日本語](README.ja.md)
**⚠️ 破坏性变更免责期：至 2027-09**（计划书 §12.5、ADR-0005）。

## 在验证什么命题

计划书 §3.4 的**第 1 类仲裁维度**：Hebbian ↔ e-prop 的**冲突检测与权重调节**。
（第 2–3 类是另外两对规则、第 4 类是"自主处理 vs 调用 LLM"的调度决策——都排在后面阶段。）

冲突判定用计划书 §3.4 的原话：

> 冲突判定：计算两条规则对同一突触权重更新方向的余弦相似度，夹角超过 90° 判定为冲突。

对应的验收口径是 §七 第二阶段的「仲裁器使双规则冲突事件减少 50% 以上」，以及 §九 的
「三规则协同 / 冲突事件比例 < 20%」。

## 当前结论

**冲突判定做出来了，ES 仲裁器做出来了，但「冲突事件减少 50%」这条在人造数据上是平凡成立的
——它验不了什么。**

1. **逐突触余弦是退化的，逐行余弦才有夹角。** 单个标量的"方向"只有正负，所以逐突触余弦
   **恒为 ±1**，「夹角 > 90°」退化成「符号相反」，阈值没有意义。要让"夹角"有实义，得在
   **一组突触**（例如某个突触前神经元的整行出边）上算余弦。两种口径都实现了
   （`axis=None` 逐突触 / `axis=1` 逐行，默认逐行），**不能混用**。
   ⚠️ **`axis` 跟 numpy 惯例走**：`(n_pre, n_post)` 的更新张量上，`axis=1` 是压掉
   `n_post`、**一行一个值**（突触前神经元的出边）；`axis=0` 是压掉 `n_pre`、**一列一个值**
   （突触后神经元的入边）。是两个不同的问题，要有意识地选。

2. **⚠️ 平凡解：`alpha → 0` 等于把规则 B 关掉。** 如果目标只是"最小化与 A 的冲突"，
   最优解**永远是不用 B**——那不叫仲裁，叫退化，而且它**平凡地通过 50% 那条**。
   人造 trace（`B = −A + 噪声`，两规则正面对立）上实测：**5 个种子全部 100% 降幅**，
   `alpha` 从 0.5 漂到 0.2–0.3。这是**症状，不是成绩**。
   所以：**「冲突事件降了 100%」单独看毫无信息量**，必须与 `retention`（B 还剩多少）
   **一起报**。`fit(..., min_retention=...)` 用来堵住这个退化解。
   ⚠️ 这与「测试绿着但验的是平凡性质」是同一类问题——`reduction >= 50%` 这条断言
   在退化解下恒成立，等于没测。

3. **ES 的参数化保持为 1 个标量。** Confavreux et al. 的发现是「元学习对**越来越复杂的
   共激活规则**开始失败」，所以仲裁器只调 `alpha` 一个数，是有意为之，不是没做完。

## 怎么跑出来

```bash
uv run pytest research/arbiter -q                  # 32 条测试
```

两个模块：

| 模块 | 做什么 |
| :--- | :--- |
| `conflict.py` | 冲突判定本体：`cosine_similarity` / `is_conflict` / `measure_conflict`。**不知道 Hebbian 或 e-prop 是什么**，只收两个更新张量回答一个问题 |
| `es_arbiter.py` | ES 元学习仲裁器：`blend`（按 `alpha` 混合两规则的更新）+ `fit`（用 ES 调 `alpha`）。**不依赖任何一条研究线**，所以能独立测 |

## 裁决（2026-10-18）：协同性基准是 P0，共享接口只作反事实臂

* **共享接口方案否。** 把三条规则接到同一处接口、或把 R-STDP 的更新投影到 `(784, 256)`，
  是**语义变形**——那些更新描述的不是同一个学习问题。此类做法**只允许作为标注清晰的
  counterfactual arm**，不得进入主结论。
* **优先级反转。** P0 是**协同性基准**：在两条线本来就共享的那一处权重上
  （`784 → 256` 输入映射），要求 **H 单独失败、E 单独失败、混合成功**。
  规格见 [`sweep_results/arbiter_synergy_task_spec.md`](../../sweep_results/arbiter_synergy_task_spec.md)。
* **e-prop ↔ R-STDP 反事实臂排在协同性基准之后**，且要等基准有结果再设计。
* **三方混合与调度维度维持阶段五**，本轮不动。
* 基础设施保留：43 条测试、per-row cosine、`retention` 与冲突联合报告，**照旧**。

4. **协同性基准（v3，2026-10-24，五种子）**：**MIX 的 Fisher 0.651 明显高于 H 的 0.472 与 E 的 0.331**（协同量中位数 **+0.179**，δ=0.05 与分离两条判据都过）。⚠️ **但 ES 学出来的 α 与冻结 0.5 逐位相同**——目标是整数冲突事件数，σ=0.1 的扰动改变不了它，α 一步没动。所以这一轮证明的是「**固定 50/50 混合**优于任一单臂」，**不是**「仲裁器学会了怎么混」。后续的目标函数检验（Fisher 当目标、连续代理）也都没过各自的预注册门槛，因此自适应臂**未运行**——准确说法是**不可测量**，不是**被证伪**。
   数字与对照见 [`sweep_results/arbiter_synergy/`](../../sweep_results/arbiter_synergy/README.md)。

## 已知边界

1. **只做了第 1 类（Hebbian ↔ e-prop）。** 第 2–3 类（e-prop ↔ R-STDP、Hebbian ↔ R-STDP）
   与第 4 类（调度决策）都还没做——计划书把它们排在第三阶段。
2. ✅ **已接进两条研究线**（`shared_synapse.py`）。原先这条边界是「没有一个地方把两者的
   更新送进同一个仲裁器」，现在有了：两条规则**共享同一组输入突触**（数值共享、每步同步），
   更新对齐后送仲裁器。⚠️ 但**只共享输入→隐藏那一处**，两条线的下游网络仍各自独立、
   各自的验收宽度不动（1024 与 256）。⚠️ **存储约定不同**：`ib_hebbian` 是 PyTorch 的
   `(out, in)`、`eprop` 是 `(in, out)`，所以共享是**数值共享**而非指针共享，靠每步拷贝维持
   ——`align_update` 会拦住拿反约定的情况（拿反就变成「与自己的转置比」，报出无意义的余弦）。
3. **`alpha` 混合的是更新张量，不是学习率。** 另一种做法是调节两条规则各自的学习率，
   那是"调节权重"的另一种含义；本实现取前者（与 §3.4「权重调节」的字面更近），
   **没有论证过它更好**。
4. **冲突事件的计数单位是「一个训练步」**，不是「一个突触」。一步里有一个突触冲突
   就记 1 个事件。这是 §九「冲突事件比例」的口径；若要按突触计数，用
   `ConflictReport.conflict_fraction`。
