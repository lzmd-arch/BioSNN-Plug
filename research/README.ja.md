## ⚠️ API 不安定性に関する声明

**本ディレクトリのコードは、最初の 12 か月間（2027-09 まで）は互換性についていかなる
約束もしません。**

プロジェクト計画書 §12.5 は、研究コードに破壊的変更の免責期間を設けています：

> 破壊的変更の免責期間：研究コードは最初の 12 か月間、API が不安定であることを
> 明示し、スケルトンライブラリの独立した semver は影響を受けません。

このトレードオフの理由は
[`docs/adr/ADR-0005`](../docs/adr/ADR-0005-versioning-policy.ja.md) にあります。

**実際に使うものには [`biosnn-bus`](../packages/biosnn-bus/) を使ってください。** これは
semver に従っており、本ディレクトリのコードには意図的に一切依存していません
（[`ADR-0001`](../docs/adr/ADR-0001-skeleton-as-separate-library.ja.md) 参照）。

## 現在の規模

**本プロジェクトは現在 256 個のスパイキングニューロンで動いています。**

三本の検証ラインのネットワーク（数値は各ラインの CLI 既定値＝受入設定から）：

| ライン | ネットワーク | 規模 | 種類 |
| :--- | :--- | ---: | :--- |
| W1 知覚層 | 3 層 × 1024 | **3,072** ユニット | レート型 LReLU——**スパイキングニューロンではありません** |
| W2 認知層 | 単層リカレント | **256** ニューロン | **ALIF スパイキングニューロン**（β=0.07） |
| W3 実行層 | 集団 Critic + Actor | **64** ユニット（+2 行動） | レート型ユニット |
| 骨組みライブラリのデモ | スパイクバス | 128 次元（プラグイン 32 + 128 チャネル） | プラグイン符号化ユニットで、**ニューロンではありません** |
| W3 スパイク化（第三段階） | LIF 出力層 + 集団 Critic | 64 ユニット | **スパイキング**（LIF）。10 シードで 0/10 が合格 |
| W4 クロスモーダル検索 | 凍結前端 + 連想層 | 512 / 768 次元の特徴 | スパイキングニューロンなし。連想層は外積または delta 規則 |

**本当の意味でのスパイキングニューロン**：W2 の **256** 個に加え、第三段階のスパイク実行線の
**64** 個（未合格：10 シードで 0/10）。W4 にはスパイキングニューロンはなく、凍結前端 + 局所連想である。

⚠️ **計画書の目標とは約二桁違います**。「フェーズ 1 完了」を「規模ももうすぐ」と読み違えない
よう、ここに並べて書きます：

| | ニューロン規模 |
| :--- | ---: |
| **現在（実測）** | **256** |
| §2.2 認知コア「初期約 5 万ニューロン」 | 50,000 |
| §九 フェーズ 2 目標 | 100,000 |
| §九 フェーズ 4 目標 | 500,000 |

差は約 **195 倍**。W1 の 3,072 ユニットが最も多いですが、レート型なので
**「スパイキングニューロンの規模」には数えません**。拡大の道筋・メモリ制約・三つの縮退経路は
計画書 §6.2/§6.3 にあり、**規模の実測実験はまだ始まっていません**（§九 は「10 万」を
フェーズ 2 に置いています）。

プロジェクト計画書 §七 のフェーズ区分に従い、本ディレクトリは**第 1 フェーズ**から
埋めていきます：

| フェーズ | 内容 | 対応するプロジェクト計画書 |
| :--- | :--- | :--- |
| 第 1 フェーズ（1-3 か月） | e-prop 認知コア（ALIF + 適応閾値；計画書が挙げた Trace Propagation は考証の結果**不採用**、[ADR-0010](../docs/adr/ADR-0010-eprop-quadratic-storage-and-trace-propagation.ja.md) 参照）；カーネル化 IB-Hebbian 知覚層（除算正規化を含む）；R-STDP 実行層（Critic を含む） | §七 第 1 フェーズ、§三 |
| 第 2 フェーズ（4-8 か月） | 二規則の協調、TAAF 高速微調整、ES メタ学習アービタ | §七 第 2 フェーズ |
| 第 3 フェーズ（9-15 か月） | 三規則閉ループ、継続学習ベンチマーク | §七 第 3 フェーズ |
| 第 4 フェーズ以降 | 神経新生、規模拡大、メタ認知ゲーティング | §七 第 4 フェーズ |
| 第 3 フェーズ（一部） | **実行層のスパイク化**（`rstdp_spiking/`：LIF + 実 Δt 窓の STDP + 線形 TD／TD-LTP 集団 Critic）と**クロスモーダル検索**（`retrieval/`：データセット、符号化、五つの連想規則、回復率の基準） | §七 第 3 フェーズ |
| 第 3 フェーズ（未着手） | 音声プラグイン、継続学習ベンチマーク、アービタの三規則への拡張 | §七 第 3 フェーズ |

各モジュールの docstring の先頭には、免責期間と満了日を明記する必要があります。

## ディレクトリ規約

```text
research/
├─ common/                  # 領域知識を持たない基盤（シード / デバイス / 指標 / 再現記録）
├─ components/              # パラメータ化できる領域部品（CartPole 状態符号化 など）
├─ <トピック>/
│  ├─ README.md
│  ├─ <実装>.py
│  └─ tests/
└─ ...
```

**対外結論を持つトピックには README が必須です**。次の 3 点を明確に書きます：**どの命題を
検証しているのか**、**現時点の結論**、**どうやって実行して結果を出すのか**。プロジェクト
計画書 §9 の評価指標表が、これらの結論の受入基準です。

例外は 2 種類だけで、いずれもここに登録します（別の場所に重複して書きません）：

* `common/`——純粋な基盤（シード / デバイス / 指標 / 再現記録）。用法の約束は各モジュールの
  docstring にあり、ディレクトリ README はそれを繰り返すだけになります。
* **結論がすでに証拠層にあるトピック**——結論はデータと共に移動し、ディレクトリ側に
  複製を作りません。現在は `continual/` が該当します
  （結論は [`sweep_results/continual_cifar100/README.md`](../sweep_results/continual_cifar100/README.md)）。
  `cognitive/` はまだ整備中で対外結論がないため、結論が出た時点で上の第 1 規則に従って
  README を追加します。

**依存は一方向だけ：主題 → `components/` → `common/`。**

* `common/` は**領域知識を持たない基盤**で、主題も `components/` も import しません；
* `components/` は**パラメータ化でき、結論を出さない領域部品**で、`common/` だけに依存します；
* **主題どうしで許される辺は二種類だけ**：①`arbiter/`・`continual/` のように**組み合わせや
  ベンチマーク自体を目的とする**主題が、相手の**パッケージルートが公開する名前**を読む
  （`from research.eprop import EPropLearner`）。サブモジュールには触れない。②何も読まない。

どちらにも当てはまらない共有要求の正解は、その部分を `components/` の部品に引き上げ、
**明示的なパラメータ**で両者の値を分けることです——コードを複製することではありません。
複製の代償は一度払っています：二つの符号化式は文書で「同型」と書かれていましたが、
実際の値域は違い、それを検出する仕組みはありませんでした。

この規則は [`tests/test_architecture.py`](../tests/test_architecture.py) が AST で検査します。

`research/` は**パッケージ**であり、散らばったスクリプトの寄せ集めではありません。
そうすることで初めて、三本の線が `common/` にある「口径を揃えねばならないもの」を
共有できます。したがって入口スクリプトは常に**モジュール方式**で実行します：

```bash
uv run python -m research.<topic>.<script>
```
`python research/<トピック>/<スクリプト>.py` を直接実行しても動きますが、その場合
`sys.path` に入るのはスクリプトのあるディレクトリでありリポジトリ直下ではないため、
`research.common` を import できません。

テストは各トピックの `tests/` に置きます。`pyproject.toml` の `testpaths` は既に
`research` を含むため、ローカルの `uv run pytest` が拾います。CI では
`research-smoke` job（torch が必要）が担当し、スケルトンライブラリとリポジトリの
ツールチェーンは `test` job が担当します——それぞれが実行できる半分を走らせます。

## 最小再現スクリプト

プロジェクト計画書 §12.3 は「中核となる文献ごとに 1 つの `examples/paper_<name>.py` を
用意する」ことを求めており、これは「論文では動くと書いてあるのにリポジトリでは動かない」
を食い止めるためのものです。こうしたスクリプトは [`examples/`](../examples/) に置き、
ここには置きません——CI から直接実行できる必要があるからです。

## 提出前の追加要件

リポジトリ共通の提出前チェックリスト
（[`CONTRIBUTING.md`](../CONTRIBUTING.ja.md) 参照）のほかに、研究コードには次が必要です：

- 実験の結論には完全な環境記録を添付する
  （[`docs/reproducibility.md`](../docs/reproducibility.ja.md) 参照）；
- 外部の結論を引用する場合は、[`docs/references.md`](../docs/references.ja.md) に登録し、
  検証ステータスを記す；
- 代理勾配ベースラインとの比較では**ギャップの定量報告**を出す——プロジェクト計画書 §9 は
  「代理勾配ベースラインとのギャップの定量報告を出すこと」を第 2 フェーズの受入項目として
  おり、追いつくことまでは求めていません。
