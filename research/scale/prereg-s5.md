# 预注册：规模实验 S5——评测分批之后，规模能到多大（2026-11-03）

**状态：判据先落盘，代码未跑。**

## 为什么

S4 推翻了 S1/S3 的显存结论：16,384 的 **7,489.5 MiB 里有 7,309 MiB 是一次
`predict(1000 个测试样本)`**，而**训练一次 update 只要 129.9 MiB**。

所以"16k 是 8 GB 终点"作废。S5 要问的是：**把评测分批之后，这条路径能到多大。**

## 改一处实现（评测分批，不改模型）

`scripts/run_event_driven_10k.py` 加 `--predict-chunk`（默认 0 = 一次全喂，行为不变）：
给了就按块调 `model.predict` 再拼接。这样**测试集不变（仍是 1000 条）**，只是不再一次性驻留。

这是实现改动，所以要单独预注册——它不改变可比性（同样的 1000 条测试样本），只改变显存峰值。

## 规模点与预算

- **32,768** 与 **65,536**（16,384 已有，作基准）；
- 其余与 S2/S3 完全一致：完整 sMNIST、**2 epoch**、种子 0、batch 8、fan-in 32、**test-samples 1000**；
- `--predict-chunk 100`。

## 判据

| # | 判据 | 门槛 |
| :--- | :--- | :--- |
| **S5-0** | 分批之后放得下 | 峰值 < **8,000 MiB**；OOM 如实记 |
| **S5-1** | 规模还在付钱 | `acc(65536) − acc(16384) > 2pp` |
| **S5-2** | 时间没爆 | 每个点的耗时 ≤ **1.5 ×** 16,384 的 1,071 s |

## 跑之前的预期

- **S5-0 应当过**：update 129.9 MiB，评测分 10 块每块 ~730 MiB；
- **S5-2 应当过**：实测 `s/update` 在 1024 与 16384 上几乎相同（0.075 vs 0.071 s），
  说明每步成本由固定开销（28 个时间步的 Python 循环）主导，不随 `n_rec` 长；
- **S5-1 不确定**：S3 里 8k→16k 只涨 2.3pp，再翻两番可能还是 2–3pp。若不过，
  说明**精度**这条轴到顶了（而不是显存到顶）——那是完全不同的一条结论。

## 死亡条件

- S5-0 不过 → 分批没起到作用，回头查 `predict` 的实现，不换 batch；
- S5-1 不过 → 精度在 16k 附近饱和；规模轴的意义变成"同样精度下更省显存/时间"，
  而不是"更大更准"。

## 不做的事

- 不改 epoch、不改学习率、不改 fan-in；
- 不把 32k/64k 的性能与 W2 的 250-epoch 数字比较。
