# 预注册：规模实验 S4——**显存到底花在哪**（2026-11-03）

**状态：判据先落盘，代码未跑。**

## 为什么先做这个

S3 把加宽这条轴走到底了：16,384 神经元吃掉 **7,489.5 MiB**（93.6% 的预算），
而**稀疏权重只有 524,288 个——按 fp32 才 2 MB**。

**7.5 GB 里有 99.97% 不在权重上。** 在搞清楚它花在哪之前，谈 fan-in、batch 或别的轴都是猜。

## 这一版要回答的三件事

1. **显存的构成**：权重 / 状态 / 资格痕迹 / 逐步激活 / 自动求导中间量，各占多少；
2. **它随什么长**：`n_rec`、`batch`、时间步 `T` 各是什么指数；
3. **哪一项是主项**——只有知道这个，才知道下一个杠杆该拉哪里。

## 做法

- 用 `torch.cuda.memory_summary()` 与 `max_memory_allocated` 在**同一次前向+一次 update** 上取样；
- 规模点：8,192 与 16,384（已有峰值可对账）；
- 变体：`batch` 8 → 1、`T` 固定（sMNIST 是 28）；
- 只跑 600 个样本、1 个 epoch 的**一次 update**，不做训练。

## 判据

| # | 判据 | 门槛 |
| :--- | :--- | :--- |
| **S4-0** | 账要对得上 | 主项之和 ≥ 实测峰值的 **90%**（对不上就说明还有没找到的大头，如实写） |
| **S4-1** | 随 batch 怎么变 | `batch 8 → 1` 时峰值降到 **≤ 1/4**（说明主项与 batch 线性相关，否则不是） |
| **S4-2** | 主项识别 | 明确指出一个主项，并给出它在 16,384 时的绝对大小 |

S4-0 不过**不算失败**——"账对不上"本身就是结论，会改变下一步。

## 不做的事

- 不改实现（这一轮只测不改）；
- 不为了"看起来好看"关掉 autograd 或换 inference 模式——那是另一个配置，要单独预注册。

## 跑之前的预期

**我预期主项是自动求导保留下来的逐步中间量**（`(batch, T, n_rec, fan_in)` 这一族），
按 `8 × 28 × 16384 × 32 × 4B ≈ 470 MB` 一份，若有十几份就是 GB 级。

若真是这样，下一个杠杆就不是"加神经元"，而是**减小 fan-in 中间量的驻留**（例如分块或 checkpointing）——
那会是另一条完全不同的路。
